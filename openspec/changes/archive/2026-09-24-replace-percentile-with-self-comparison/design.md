# Design

## Context

现状（动机见 proposal.md）：百分位从「演示值」改成「真实池子」之后，散落在
`percentile_service` / `scoring` / `attempt_service` / `report_service` 四处后端逻辑、
三个 Pydantic 模型（`AttemptSummary`、报告文档、归档列表项）与三个前端文件里。
本次要把这条链路整体换成「与自己的历史比较」。

几个会影响方案形状的既有事实：

- `attempts` 表**已经有** `attempt_no` 列，含义是「**同一份卷轴**的第几次挑战」
  （`quiz_repository.next_attempt_no`），并由响应顶层 `attempt_no` 返回。
  本能力引入的「这是**该用户**的第几局」是另一个量，**命名必须与它区分**，否则两个
  「第几局」会在同一个响应里互相打架。
- `attempts` 已有 `deleted_at`，且 FR-B5 定了口径：删除记录「仅移除记录，不影响整体统计」。
- 报告不是独立统计表：`ReportDoc` 在读取时由报告快照 + `attempts` 行重建，
  所以「报告里那一格」可以走与结算完全相同的计算路径。
- 本次的净效果是**删两列**，不新增任何列 —— 这条约束直接决定了下面的 D1。

## Goals / Non-Goals

**Goals:**

- 一次挑战的自我比较状态由**一个纯函数**判定，结算与历史回看走同一条路径。
- 不新增任何数据列。
- 前端零比较逻辑：只做「状态 → 文案」映射。
- 删列不可逆动作有可核对的留底。

**Non-Goals:**

- 不做「最近 N 局趋势图」（proposal 已列为后续可选）。
- 不做同副本挑战者之间的比较。
- 不改判题 / XP / 金币 / 勋章链路。

## Decisions

### D1 状态不落库，读取时按「截至该局之前的历史」重算

考虑过三种做法：

| 做法 | 否决理由 |
|---|---|
| 像 `percentile` 那样落一列存状态 | 本次目标就是净删列；且快照会变成假话 —— 用户后来又刷新了纪录，旧那局的报告仍宣称「这是你的最好成绩」 |
| 按「当前全部历史」重算（含该局之后的局） | 历史报告会随新局变化，「刷新纪录」这种瞬时事实被后来的成绩改写 |
| **按「id 小于该局的记录」重算（采用）** | 结算时本局尚未落库 → 基准取全量；回看历史 → 基准只取该局之前的。同一函数、两种入口，且历史报告不随时间漂移 |

比较基准用 `id`（自增写入序）而不是 `finished_at`：客户端时间戳会被夹取，
而写入序等价于用户实际答题的先后。

### D2 一个函数、两个入口

新增 `backend/app/services/progress_service.py`：

```python
def for_attempt(
    session: Session,
    *,
    user_id: int,
    correct_count: int,
    before_attempt_id: int | None,
) -> AttemptProgress
```

- 结算：`before_attempt_id=None`（本局未落库）。
- 历史回看：`before_attempt_id=该局 id`。

只发两条查询：紧邻上一局（`id < 基准 ORDER BY id DESC LIMIT 1`）、
此前最好的一局（`ORDER BY correct_count DESC, id DESC LIMIT 1`），
外加一条 `COUNT(*)` 得到「这是你的第几局」。

⚠️ 结算时**不能**先落库再算：落库后本局就成了「历史最好」的候选人，
拿自己跟自己比，`record` 永远不可能成立。

### D3 契约：嵌套一个 `progress` 对象

```jsonc
"progress": {
  "state": "record",              // first | record | tie_best | better | same | worse
  "attempt_count": 3,             // 这是该用户的第几局（含本局）
  "delta_vs_prev": 2,             // 本局 − 上一局 的答对题数（正数为进步）
  "best":     { "correct": 4, "total": 5 },  // 首局为 null
  "previous": { "correct": 2, "total": 5 }   // 首局为 null
}
```

选嵌套而不是在 `summary` 里再加六个扁平字段：语义成组、删除时是一个整体、
且 `delta_vs_prev` 由服务端给出后前端连减法都不用做（两页必然逐位一致）。

### D4 判定顺序与比较量

优先级 `first` > `record` > `tie_best` > `better`/`same`/`worse`，
比较量是**答对题数**（`correct_count`），不是 `accuracy`：这一格的文案本来就是
「答对几题」，用正确率比较会立刻把百分比请回来。

已知局限见 Risks 第一条。

### D5 已删除的记录沿用 FR-B5 口径：计入

与百分位时代的处置保持一致。若这里过滤 `deleted_at`，用户删掉一条旧记录就会
改变自己的「最好成绩」与历史报告的状态 —— 正是 FR-B5 禁止的那件事。

### D6 先删引用，再删列

`attempts.percentile` 现在仍被提交链路与回放链路读，**先删列会让接口 500**。
顺序固定为：删代码引用 → 删接口字段 → 跑闸门 → 备份两列现有值 → 执行幂等 DDL → 复核表结构。

DDL 幂等写法（沿用 `05_*.sql` 的风格）：先查 `information_schema.COLUMNS`，
存在才 `ALTER TABLE ... DROP COLUMN`。

### D7 文案集中一份 `PROGRESS_COPY`，状态映射放共享工具

结算页与冒险日志页**共用同一组文案常量**（不是各写一份）：项目已有先例 ——
复习提醒那条注释写着「两处各写一份必然会出现两种说法」。结算页只渲染标题行，
冒险日志页渲染标题行 + 说明行。

映射函数（`state → { title, note }`）放前端共享位置，两页调用同一个。

「社团」的处理：统计句里的用法随这一格一起消失；`社团大厅` / `返回社团大厅` 这类
世界观包装保留。

### D8 视觉沿用现有结构，只换内容源

那一格的容器、精灵、进度条都保留：

- 进度条宽度改为**本局正确率**（不再表示分位）—— 与上方环形图同源，不再是与他人比较的结果。
- 胶囊位置原来渲染 `percentile_label`（档位名「中上」）。现在只在
  `state === 'record'` 时渲染「新纪录」，其余状态不渲染 —— 与原来
  「`percentile_label === null` 就不渲染」同构，CSS 结构不用动。
- 说明行由「按社团里 N 位冒险者的最佳正确率计算」换成进度说明。
- 颜色：`record` 用强调色（与既有的 `stamp gold` 同源），其余状态用中性色。

## 与项目硬约束 / 原型的对照

- **后端 TDD**：`progress_service` 与状态的判定顺序是纯函数，先写测试（含六种状态与
  优先级冲突用例）再写实现；删列任务本身不可 TDD，靠「迁移可重跑」这条需求兜底。
- **零视觉漂移**：本次**唯一**允许变化的 UI 就是这一格，改动集中在文案与颜色，
  容器与进度条结构不动。验收要给实跑证据（量进度条宽度、胶囊文案、说明行文本）。
- **密钥**：本次不涉及任何凭证；提交前仍跑 `tools/scan_secrets.py`。
- **接口信封**：字段在既有 `data` 内增删，不新增接口。
- **同步文档与共享用例**：`shared/scoring-cases.json` 里的 `percentile_cases` 已在
  09-23 移除（前端不再算分位），本次无需再动；新增的进度判定若进共享用例，
  需同时给出 TS 侧实现 —— 本设计**不**要求前端实现判定，故不进共享用例。
- **文案与实现冲突时改文案**：本方案整条就是在执行这条。
- **交付页面连入口**：本次不改路由与入口，两页原有入口不变。

**与原型冲突（需知情接受的偏离）**：原型 `03-冒险日志.html` 第 1 屏写着
「本局超过社团里 72% 的冒险者」，本方案撤掉它。这是有意偏离，按项目惯例登记进
`frontend/src/constants/copy.ts` 文件头与 `docs/MVP开发计划.md`，避免以后被当成
bug「修」回去。此项已与用户确认（选定方案一）。

## Risks / Trade-offs

- [**题量不同的副本之间比「答对题数」不公平**：5 题答对 5 与 10 题答对 6，前者状态是 `better` 但正确率更低]
  → 文案强制带分母（「答对 4 / 5 题」「比上一局多答对 2 题」旁始终有最好成绩的完整题量），
  让题量差异可见；**知情接受**，不引入百分比。
- [删列不可逆] → 执行前把两列现有值（含 25 条历史）导出到
  `D:\备份\WorkBuddy\knowsaga-club\2026-09-23\`，核对行数与文件大小后再 DROP；DDL 幂等可重跑。
- [旧记录没有状态数据] → 无需回填，这是 D1 的直接好处（读取时重算）。
- [历史报告的状态会因「删除记录」而变化] → 由 D5 的口径统一决定，已在需求侧留痕。
- [前端删字段若漏改会 tsc 失败] → 这是期望行为，闸门会拦；`noUnusedLocals` 已开，
  留下的死分支也会一起报出来。

## Migration Plan

1. 后端：先写测试（进度判定六态 + 优先级）→ 实现 `progress_service` → 删百分位链路。
2. 前端：`PROGRESS_COPY` + 映射函数 + 两页渲染 + 删类型字段。
3. 全量闸门：pytest / tsc --noEmit / check:scoring / scan_secrets。
4. 备份两列现有值到用户指定的备份目录，核对行数。
5. 执行 `backend/sql/06_*.sql`（幂等），用 `SHOW COLUMNS` 复核两列已不存在。
6. 重启 `:8000`（改了服务端逻辑，不重启会按旧逻辑验收），起后端 + 跑端到端脚本 +
   浏览器实跑结算页与冒险日志页。

**回滚**：代码可直接回滚；两列的数据以第 4 步的导出文件为准（不回填进库，
如需恢复用导出文件重建列并导入）。
