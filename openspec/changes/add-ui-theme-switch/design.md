# Design

## Context

- `frontend/src/styles/tokens.scss` 是全站颜色的**唯一来源**：实测 127 个 `$` 变量声明（其中 66 处 `var(--k-*, …)` 引用，去重 64 个令牌），45 个 `.scss` 通过 `@use` 引用它。SCSS 变量在**编译期**被替换成字面量，产物里不再有变量名 ⇒ 运行时切换颜色在当前机制下不可能。这是必须先动机制的原因（动机见 proposal.md - Why）。
- **实测（非推断）**：全仓没有任何 SCSS 颜色函数（`rgba()` / `mix()` / `lighten()` / `darken()` / `transparentize()`）作用在颜色 token 上；唯一命中的 `math.round($proto-px)` 是尺寸换算。这条决定了「把 token 值换成 `var()`」不会撞上「SCSS 无法对 `var()` 求值」的编译错误。
- 31 个页面里 30 个以 `PhoneShell` 为根，其根节点是 `<View className='page'>`；`custom-tab-bar` 是独立组件，不在 `PhoneShell` 内。
- **微信 WXSS 不支持属性名选择器 `[...]`**（官方文档明写，且推荐只用 class 选择器）⇒ 挂载点只能是 **class**。
- **步骤 0 地基已实测通过**：把 `var(--k-spike)` 与带兜底的 `var(--k-spike-none, <色>)` 注入构建产物后，postcss 原样保留、未被改写（编译期无风险）；在微信开发者工具里肉眼确认「社团大厅顶部标题变红 + `‹` 返回箭头变蓝」⇒ **运行时 WebView 认 `var()`**。
- 后端已有 `UserSettings` 表与 `GET|PATCH /users/me/settings`；前端已有 `services/settings.ts` / `store/useAppStore.ts` / `utils/cache.ts` 的设置链路 ⇒ 本次是**扩展**，不是新建。

## Goals / Non-Goals

**Goals:**

- 让「换颜色」成为运行时可切换的能力，同时保证**默认外观逐项不变**。
- 色值只有一个真源；生成物与真源不一致时能被机检拦住。
- 新增的 4 套主题（含一套暗色）满足 WCAG AA，且不靠兜底掩盖问题。

**Non-Goals:**

- 不做主题的在线下发 / 热更新 / 用户自定义（预设集合是编译期常量）。
- 不改排版尺度（尺寸、字号、圆角、动效一律不动）。
- 不追求让 PNG 图标与原生弹层跟随主题（见 D8）。
- 不引入 CSS-in-JS 或运行时样式引擎。

## Decisions

### D1 换肤机制：CSS 自定义属性 + 根类名

把颜色 token 的值改成 `var(--k-xxx, <原字面量>)`；主题类只在根节点上重定义 `--k-*`。

**备选与否决理由：**

- **编译期生成 N 套作用域样式**（`.ui-theme--x .card { … }`）：产物体积 ×N，且要重写全部 46 个消费方文件。作为**回退方案**保留 —— 只有地基实测不通过才启用。
- **属性选择器 `page[data-theme]`**：微信 WXSS 不支持 ⇒ 直接否决。
- **JS 运行时改样式**：需枚举并改写每个节点，样式来源被撕裂成两处，维护与验证都更贵 ⇒ 否决。

选 CSS 变量的额外好处：**零漂移是构造保证** —— 默认主题不挂类 ⇒ 直接落 fallback，而不是靠「记得别改错」。

### D2 挂载点：`PhoneShell` 根 + `custom-tab-bar` 根

只有两个挂载点：`components/PhoneShell/index.tsx` 的根 `<View className='page'>` 与 `custom-tab-bar/index.tsx` 的根。前者覆盖 30 个页面，后者覆盖标签栏。

**备选**：每个页面各自挂 —— 漏一个就是静默的「半主题」，新增页面时也容易忘 ⇒ 否决。

### D3 改造范围：只换颜色 token 的值

`tokens.scss` 里**颜色类** token 的值改为 `var()`；尺寸、字号、字距、圆角、动效 token 一字不动。依据是 Context 里那条实测：没有 SCSS 颜色函数作用于颜色 token，所以 46 个消费方文件**无需改动**。

### D4 色值真源：`shared/ui-themes.json` → 生成 `_themes.scss` + parity 校核

需要色值的有两个运行时：WXSS（CSS 变量）与 JS（canvas 取色）。两份手抄必然漂移，所以：真源 `shared/ui-themes.json` →（构建期脚本）→ `styles/_themes.scss`（产物入库，同 `assets/icons/tab.ts` 的既有做法）；另配校核脚本，生成物与真源不一致即失败（沿用 `check:scoring` / `check:links` 的先例）。

**备选**：手写 `_themes.scss` —— 5 套 × 40 余个令牌，手改必错 ⇒ 否决。

### D5 默认主题不写进 JSON

`paper` 的色值就是 `tokens.scss` 里的**原字面量**（即 `var()` 的 fallback 位），不写进 `ui-themes.json`。理由：一旦默认色也抄进 JSON，就有了两处默认色定义，任一处改了都不会立刻暴露。⇒ 默认主题的唯一定义处仍是 `tokens.scss`。

### D6 持久化：服务端列 + 本地镜像

`user_settings.ui_theme VARCHAR(16) NOT NULL DEFAULT 'paper'`；前端在 Taro Storage 存一份镜像。

- **启动**：store 初值**同步**读镜像 ⇒ 首帧即正确主题（对齐 spec 的「冷启动不闪」）。
- **对账**：启动后拉一次 `/users/me/settings`，以服务端为准并回写镜像；**失败静默**（保留本地值，不打扰用户）。
- **切换**：先改 store（界面立刻变）+ 写镜像 → PATCH；失败翻回原值 + 提示。与设置页三个开关同一套纪律。
- **镜像键加入 `PROTECTED_KEYS`**：主题是偏好，不是缓存。

**备选**：只存在本机 —— 换设备就丢，不满足 spec 的「跨设备一致」⇒ 否决。

### D7 校验：白名单落在服务端

`UserSettingsUpdateRequest.ui_theme` 用**白名单**校验（同 `avatar_key` 的理由：该值决定客户端加载哪套皮肤）。不合法值 → 明确错误，**不静默兜底**（spec 要求）。

### D8 覆盖边界（如实登记，不假装兑现）

不受主题影响：标签栏 PNG 图标（烘焙了固定的未选中 / 选中两色）、微信原生 `showModal` / `showToast` / `showActionSheet`、`utils/guildCard.ts` 的 canvas 导出图、各 `*.config.ts` 的 `backgroundColor`（由 `Taro.setBackgroundColor` 在切换时补）。

⚠️ **口径修正（2026-09-27，用户实测后追问「底部图标与系统弹窗为什么不随主题变」时补）**：本条原先只写了「不受影响」，读起来像**中性**的取舍。实测后必须补一句：**其中两处不是中性，是缺陷**（读数见 D13）——
标签栏的**选中图标**在 `midnight` 下只有 **2.80:1**（低于非文本 3:1），即暗色主题里选中项几乎看不出被选中。
⇒ 「不跟随」与「不跟随且不达标」是两件事，前者是边界，后者是 bug。**已按缺陷登记，不改口径蒙混。**

### D9 暗色主题必须单独给值，并补掉硬编码色

`midnight` 是唯一的暗色主题，三处不能照搬浅色：

| 令牌 | 为何暗色要另给值 | `paper` | `midnight` |
| --- | --- | --- | --- |
| `--k-grain` | 同密度的灰噪点压在暗底上会整体提亮，读起来像**脏点** | `opacity='.13'` | `opacity='.05'` |
| `--k-hi-inset` | 卡片内高光 `inset 0 1px 0` 用近白会在暗底炸出一道亮线 | `rgba(255,255,255,.7)` | `rgba(255,255,255,.06)` |
| `--k-grad-hi` / `--k-grad-lo` | 整页背景是 `tokens.scss` 的 `board-bg` mixin（`$board` 底色 + 左上高光 + 右下暖暗 + 颗粒），暗底要把白高光压到几乎不可见、暖暗换成中性暗 | `.55` / `rgba(120,88,38,.1)` | `.05` / `rgba(0,0,0,.3)` |

> **本条的初稿有两处写错了（已按实现更正，留档以免再被引用）**：
> ① 初稿写纸纹是 `mix-blend-mode: multiply` 在暗底变噪点 —— 全仓**没有**任何
> `mix-blend-mode`，真正的机制是不透明度 `.13 → .05`。
> ② 初稿写「整页背景渐变 `--k-board-img` 换暗色叠加」—— **不存在 `--k-board-img`**
> 这个令牌，整页背景是 `board-bg` mixin 用 `--k-grad-hi` / `--k-grad-lo` / `$grain`
> 三层叠出来的。
>
> **另有一处真 bug 是实施时才发现的**：`$grain` 原本写成**裸 `url(…)`**，而生成器
> 早就在产出 `--k-grain` —— 两边看着都在，实际从未接上，暗色主题只能拿到浅色那一档
> 颗粒。编译、构建、零漂移比对**全都发现不了它**，只有切到暗色肉眼看才暴露。
> 已改为 `var(--k-grain, <原字面量>)`（`tokens.scss`，附注释）。

**并且**：`base.scss` 的 22 处硬编码色 + 5 个组件/页面 scss 的 8 处（共 30 处）必须一并纳入自定义属性 —— 否则暗色主题会在这些点上「漏白」，而这类遗漏在浅色主题下**完全看不出来**，只有切到暗色才暴露。

> **读数（实测，非估计）**：以步骤 3 之前的提交 `514f6e4` 为基线，剔除注释后按
> 「色值字面量 / 其中裸露在 `var()` 之外」统计：
>
> | 文件 | 改造前 裸露/总 | 改造后 裸露/总 |
> | --- | --- | --- |
> | `styles/base.scss` | 22 / 22 | **0** / 22 |
> | `components/AccuracyRing/index.scss` | 1 / 1 | 0 / 1 |
> | `components/ReminderPrompt/index.scss` | 1 / 1 | 0 / 1 |
> | `pages/profile/dashboard/index.scss` | 2 / 2 | 0 / 1 |
> | `pages/profile/knowledge-tree/index.scss` | 3 / 3 | 0 / 3 |
> | `pages/workshop/kb-upload/index.scss` | 1 / 1 | 0 / 1 |
> | **合计** | **30 / 30** | **0 / 29** |
>
> ⇒ 30 处裸露字面量归零。**「漏白」风险面在 `var()` 层面已闭合**，剩下的风险只可能
> 来自 JS 侧（canvas 取色，见 D10）与已登记的不可覆盖项（D8）。
> 量法脚本为一次性工具，不进仓；判据是「裸露数 = 0」这一条读数。

### D12 生成出来的令牌**必须**被消费 —— 别名会静默掐断它

**实施中发现的一类真 bug（已修，记录以免重犯）**：配方为 `--k-opt-sel-border` /
`--k-opt-ok-border` / `--k-opt-bad-border` / `--k-btn-magic-edge` / `--k-btn-gold-edge`
各产出了一份值，而 `tokens.scss` 把对应的 SCSS 变量写成了**别名**
（`$opt-sel-border: $magic;`）—— 消费方于是取 `var(--k-magic, …)`，
**那 5 份产出从未被任何地方引用**。

四套主题里恰好有四对同值（巧合），但青柠不同：

| 令牌 | 配方产出（体检用的就是它） | 别名后实际生效 | 对已选底 `#EBF6DB` |
| --- | --- | --- | --- |
| `--k-opt-sel-border`（青柠） | `#5A9900` → **3.13:1** | `--k-magic` = `#70C000` → **2.03:1** | 求解达标值被丢弃，**实际不达 3:1** |

配方源码里那句注释把意图说得很清楚：「浅色品牌（青柠）会被压深到 3:1 ——
**这正是这一项要独立成令牌的原因**」。

**这个失效为什么危险**：`check:theme` 体检的是**生成物**（`#5A9900`，达标），
于是给出**假绿**；运行时用的是别名指向的值（`#70C000`，不达标）。
编译 / 构建 / 零漂移比对同样全绿 —— 与 `$grain` 是同一失效家族：
**生成器在产出、消费方没接上**。

**修法**：那 5 个变量改为 `var(--k-*, <纸与印的对应值>)`。兜底字面量与原解析值相同
⇒ 默认主题零漂移（归一化比对仍逐字节相同，已复核），而四套新主题拿回各自求解值。

**判据（加了这条就不必靠运气发现）**：
`_themes.scss` 主题块定义的 69 个令牌 == 全仓 scss `var(--k-*)` 引用到的 69 个，
**双向零缺口**；「定义了但无人引用」必须为空。本次修完的读数是
`69 定义 / 69 引用 / 死令牌 0 / 未定义 0`。
（该判据目前是**人工量出来的**。要不要把它固化成 `check:theme` 的一条断言，
留待本变更归档前决定 —— 现在先如实登记为未固化。）

### D13 体检表缺了「标签栏」这一对 ⇒ 又一次假绿（实施后由用户实测追问才发现）

用户实测反馈：「底部图标与系统弹窗的颜色不随主题变化」。追这条时挖出**两个新的
不达项**，两者都在体检的**覆盖盲区**里 —— 165 项断言里**没有**任何一项的底色是
标签栏的底（`--k-paper-2`），所以 `check:theme` 给的是假绿。

消费点：`custom-tab-bar/index.scss` —— 未选中文字/图标色 `$ink3`、选中文字与
顶部指示条 `$magic-ink`（**原为 `$magic`，本次已修，见 ①**）；底为 `$paper2`。
图标另有烘焙死的 PNG（见 ②）。

**① 选中标签文字用了「填充色」而不是「文字色」（接线错，1 行可修）— ✅ 已修**

`custom-tab-bar/index.scss` 里选中态的文字与顶部指示条都写的是 `color/background: $magic`
（**全仓唯一**一处把填充档当文字/图形用；其余文字位一律 `$magic-ink` / `$magic-d`）。
配方为浅色品牌专门拆了 `magic-ink`，青柠却被漏在外面：

| | 值 | 对标签栏底 `#F7F7F7` | 判定（文字需 4.5） |
| --- | --- | --- | --- |
| 实际生效（`$magic`） | `#70C000` | **2.12:1** | ✗ |
| 配方已算好（`$magic-ink`） | `#497C00` | **4.70:1** | ✓ |

与 D12 是**同一失效家族**（供应方给了正确值、消费方取错了一份），但方向相反：
D12 是「生成物无人引用」，这里是「该用的那份没用上」。

**已修法**：`custom-tab-bar/index.scss` 两处 `$magic` → `$magic-ink`（文字 + 指示条）。
**为什么是 `magic-ink` 而不是 `magic-d`**：`magic-ink` 在**另外 4 套主题里与 `magic` 同值**
（纸与印都是 `#2F6BD8`），所以对默认主题逐字节无影响；`magic-d` 是 `#1F4694`，
换上去会把纸与印的指示条改色 —— 那是**真漂移**，会破坏本变更的核心承诺。
⇒ 「零漂移」在这里不是巧合，而是**选值时的硬约束**。

| 复核项 | 读数 |
| --- | --- |
| 零漂移（45 个 scss 归一化比对） | 逐字节相同 ✅ |
| `check:theme` | 165 断言 / 5 主题，退出码 0 ✅ |
| 青柠选中文字 2.12:1 → | **4.70:1** ✅（指示条同值，非文本门槛 3:1 亦达） |
| 其余 4 套主题 | **渲染值不变**（同值替换） ✅ |

**② 烘焙死的选中图标在暗色主题下不达标（改颜色救不了，只能换资源）**

图标是 10 张预光栅化 PNG，颜色在像素里（`assets/icons/png/*.png`，
未选中 `#9A8870` / 选中 `#2F6BD8`，见 `assets/icons/tab.ts` 头注释）。
标签栏的**背景与文字跟随主题**（走 `var(--k-*)`），**图标不跟随**：

| 主题 | 标签栏底 | 未选中图标 `#9A8870`（需 3） | 选中图标 `#2F6BD8`（需 3） |
| --- | --- | --- | --- |
| `paper` | `#F5EDD8` | 2.93:1 ✗（既有，同原型，不动） | 4.27:1 ✓ |
| `indigo` | `#F4F1EC` | 3.04:1 ✓ | 4.42:1 ✓ |
| `vermilion` | `#F6F6F7` | 3.17:1 ✓ | 4.61:1 ✓ |
| **`midnight`** | `#272C38` | 4.08:1 ✓ | **2.80:1 ✗** |
| `lime` | `#F7F7F7` | 3.20:1 ✓ | 4.65:1 ✓ |

`paper` 那格 2.93:1 属**既有**（图标由原型内联 SVG 烘焙而来，改动即破坏零漂移 ⇒ 保持），
但 `midnight` 那格 2.80:1 是**本次新增主题引入的**：品牌蓝在深色标签栏上发闷、
几乎看不出选中。**这不是「不够品牌」，是可用性缺陷。**

**修法（未做，待定）**：扩展 `frontend/scripts/rasterize_tab_icons.py`
按主题生成图标集（色取自各主题的 `ink-3` / `magic-ink`），`tab.ts` 改为
「主题 → 图标集」索引。10 张 → 50 张，体积 6.8 KB → ~34 KB（可忽略），
且沿用已验证的 PNG 路径（不重新引入 `image` + SVG 的三条未兜底限制）。

**判据（应该补、现未补）**：给 `CHECKS` 加两条 —— `ink3 on paper2`、`magic-ink on paper2`
（底色用标签栏真实底色）。**消费侧已改完（见 ①），但体检表本身仍是盲的** ——
下次谁再把这里的色值换错，165 项断言一样全绿。
另：`ink3 on paper2` 在 `paper` 下是 2.93:1（既有 sub-AA，登记不判红），
四套新主题 4.63–5.04:1 全达标。

**系统弹窗为什么不跟随（机制，非取舍）**

- **小程序端**：`showModal` / `showToast` / `showActionSheet` 是微信**原生**组件，
  不在 WebView DOM 里，CSS 完全够不到。可传的参数只有 `showModal` 的
  `confirmColor` / `cancelColor`；`showToast` **一个颜色参数都没有**。
- **H5 端**：Taro 的 `showModal` / `showToast` 确实是 DOM 实现
  （`@tarojs/taro-h5/dist/api/ui/interaction/modal.js` / `toast.js`），但**每个颜色都是内联 `style`**
  （`modalStyle.background: '#FFFFFF'`、`textStyle.color: '#808080'`、默认 `confirmColor: '#3CC51F'`）。
  内联优先级高于任何类选择器 ⇒ 加 `.taro-modal__content { background: var(--k-paper) }` 也**不会生效**。
- ⚠️ **反直觉结论，刻意不做「让弹窗按钮跟随主题」**：原生弹窗的**底永远是系统浅色/白**
  （H5 侧就是写死的 `#FFFFFF`；小程序侧由系统深浅色决定，不受我们控制）。
  把暗色主题的 `bad` 贴上去反而更差：`midnight` 的 `#E56F5E` 对白底只有 **3.10:1**（低于 4.5），
  而现在硬编码的 `#A63A2E` 是 **6.43:1**。⇒ 弹窗是**系统界面**，跟着系统配色才是对的；
  要真正自绘换肤得替换 `showModal` 4 处 + `showToast` 约 30 处调用点，属**另立变更**。

## 项目已知坑的规避

- 前端禁 `style={{}}` 内联对象、长度不许写死 ⇒ 主题类与 `--k-*` 一律走 **class + SCSS**，不在 JSX 里写内联样式。
- Taro 的失效大多是**静默**的 ⇒ 交付前真浏览器跑一遍并**量 DOM / 计算样式**，不靠肉眼。
- 页面必须有一处挂载即发首帧请求 ⇒ 本次不改任何页面的请求逻辑，只改颜色来源。

## Risks / Trade-offs

- [暗色主题漏白：某处硬编码色没纳入自定义属性，在暗底上显示为刺眼白块] → `base.scss` 的 22 处与 5 个组件/页面 scss 的 8 处（共 30 处）一并改造，并在浏览器里逐屏检查暗色主题的对比与溢出。**已实测：裸露字面量 30 → 0**（读数见 D9）。
- [生成物与真源漂移] → parity 校核脚本进闸门，不一致即失败。
- [**生成物被产出但无人消费**（别名把令牌掐断）：体检看的是生成物 ⇒ **假绿**，运行时用的却是别的值] → 本次已实发一次（见 D12，青柠选中态描边）；判据是「定义数 == 引用数、死令牌 0」。
- [**体检表本身有盲区**：某项的底色不在 `CHECKS` 里，则该处无论多差都永远绿 —— 与 D12 同类的第二种假绿] → 本次已实发一次（见 D13：标签栏底 `paper2` 上的文字从未被任何一项覆盖，青柠选中文字实测 2.12:1，`lime` 与 `midnight` 各有不达项）。**消费侧已修（青柠 2.12 → 4.70），但体检表仍未补这两条 —— 盲区还在。** 教训：体检只覆盖它列出的组合，不是「全站都查过了」。
- [烘焙资源（PNG 图标）在新主题下不达标] → 见 D13②：`midnight` 选中图标 2.80:1。修法（按主题生成图标集，或改用可着色的矢量 + `mask`）**待定**，未做前如实登记为已知缺陷，不得宣称「5 套主题视觉一致」。
- [首屏闪回默认主题] → 本地镜像**同步**读作 store 初值。
- [主题类漏挂导致半主题] → 只有两个挂载点，且都纳入验证清单（标签栏单独看一眼）。
- [WCAG 压线：求解停在 4.50 / 3.00，8bit 量化后翻红] → 求解按「门槛 + 安全余量」，判定发生在量化后的色值上（沿用 v3 的教训）。
- [微信端不生效但 H5 正常] → 步骤 0 已在开发者工具确认 `var()` 生效；交付前仍要求双端各跑一次。
