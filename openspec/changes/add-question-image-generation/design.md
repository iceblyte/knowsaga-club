# Design

> 目标：在**不改变既有出题 / 取材 / 评分 / 复盘链路**的前提下，为题目加上配图。
> 下面 D1–D11 是决策与理由，D12 是与现状的冲突点，D13 是对 `config.yaml` 硬约束的逐条回应，
> D14 是不做的事，**D15 是 2026-09-26 的生图模型更换（`qwen-image-2.0` → `z-image-turbo`）**。

## D1 触发方式：新增请求级入参 `generate_images`，默认 `false`

配图是**这一次召唤**的选项，不是账号级偏好 —— 与 `use_search` 同一层。理由：

- 与「用户下次进来应当重新表达一次意愿」一致（`useAppStore` 里 `useSearch` 的注释已立此规矩）；
- 账号级偏好要落库、要有设置入口、要考虑跨设备同步，而配图是「这一局想不想要」；
- 默认 `false` ⇒ 不传该字段的调用方（含所有既有测试、`scripts/verify_*.py`）**行为逐位不变**。

## D2 调用粒度：**每题一次调用**，不是「一次 `n=6`」

需求原文写「同步调用，单次请求最多生成 6 张」+「并发调用生图 API，5 道题的配图同时生成」。
这两条在实现上互斥：一次生图请求只带**一个** prompt，`n=5` 得到的是**同一主题的 5 张近似图**，
做不到「每道题配与自己相关的图」。

⇒ 实现取**每题一次调用（`n=1`）+ 5 个请求并发**。「单次 6 张」的上限对本题量（3–5 题）
不构成约束，所以放弃它没有代价。事实依据：当前模型 `z-image-turbo` 官方写明
「图像张数：**固定 1 张**」——`n>1` 在它身上本就不存在；接口也只有同步一种（无异步 task 接口）。

> 本决策最初按 `qwen-image-2.0` 写下（那一族 `n` 支持 1–6、`qwen-image-max/plus` 固定 1）。
> 2026-09-26 换模型（**D15**）后结论不变、反而更贴合。

## D3 并发、超时与总预算：都必须有界

上游 SDK 不保证自带超时（与 `llm/search/agent.py` 对 `langchain-tavily` 的判断同源）。
所以：

| 项 | 默认 | 理由 |
|---|---|---|
| `image_max_workers` | **2** | 与出题链共用进程；无界线程会把一次流量高峰打穿。**2026-09-26 由 3 下调**（实测 429，见 D17） |
| `image_timeout_seconds` | 20 | **单张**的上游超时。生图比 LLM 慢，给得比 `search_tool_timeout_seconds` 宽 |
| `image_budget_seconds` | 45 | 整段生图的**总预算**。超时即放弃剩余图片，**不阻塞落库** |

总预算的存在理由与 `quiz_generation_budget_seconds` 相同：宁可少几张图，
也不能让「副本召唤中」空转两分钟。总耗时上限 = 单张超时 + 预算（并发按批推进）。

## D4 Prompt 构建：只用**知识点 + 题干主题词**，禁选项 / 答案 / 文字

**冲突点**：题干全文相关性最强（英语单词配实物图正是这个诉求），但
「下面哪个是苹果」这类题的题干会把答案直接画出来 —— 配图就成了泄题。

⇒ 取折中：Prompt 只由 `knowledge_point` + 从题干里抽出的主题词构成，
安全性靠两道**结构**防线承担：选项文字不进提示词、题干整句不进提示词
（后者是 D16 补的 —— 题干整句进提示词既会被当标题渲染，也常携带答案线索）。

⚠️ 「画面不出现任何文字」**不在**这里靠"把禁令写进提示词"实现 ——
D16 实测那样做适得其反（禁令本身被画了出来）。它现在是负向通道 + 风格词的任务。

同时关掉上游的 `prompt_extend`（默认 `true`）：它会改写提示词，
「与题干匹配」这件事会被模型改跑偏，而我们的 Prompt 已经足够具体。

## D5 存储：只存 URL，二进制先下载再上传 COS

- 上游返回的图片 URL **有效期仅 24 小时**（官方明确），所以「转存」不是优化项而是必需项。
- 下载 → 用 `cos-python-sdk-v5` 的 `put_object` 上传 → 用 `https://{bucket}.cos.{region}.myqcloud.com/{key}` 拼**永久** URL。
- 数据库只存这一列 URL（`VARCHAR(512)`），**不存二进制**：图片体积会让 `questions` 表迅速膨胀，
  而 MySQL 不适合当对象存储。
- key 规则 `questions/{quiz_id}/{seq}-{hash8}.jpg` —— 带 `quiz_id` 便于按卷轴清理，
  带短 hash 避免同卷轴重跑时覆盖。
- 下载时校验 `Content-Type` 与字节数（上限 8 MB），**下载失败等同生图失败**（不传半张图）。

## D6 配额：独立小表 + 业务日 + 原子自增，不复用 `core/ratelimit.py`

`app/core/ratelimit.py` 是**进程内滑动窗口**，做「每人每天 20 张」会有两个不能接受的后果：
重启即清零、多实例各算各的。⇒ 建一张 `image_quota_usage(user_id, biz_date, used_count)`，
联合主键，`INSERT ... ON DUPLICATE KEY UPDATE used_count = used_count + N` 原子自增。

三段式：

1. **预检**（`reserve`）：在 `create_task` **之前**扣减。不足则抛错并给友好文案 ——
   用户不必等十几秒才知道没图（与 `_resolve_kb_scope` 的「建任务前校验」同一纪律）。
2. **结算**（`settle`）：任务成功后按**实际成功张数**结算，把没生成出来的张数退回去。
3. **退还**（`release`）：任务整体失败（出题失败 / 被取消）时全额退回。

业务日按 `app_timezone` 判定（与「今天」「连续天数」同一口径），
**不用 UTC 日期** —— 否则中国用户的「今天」会在早上 8 点重置。

### D6.1 超额的错误码取 `4290`，不是 `4001`（对 tasks 初稿的修正）

`tasks.md` 初稿写的是 `AppError(4001, 友好文案)`，实现时改成 `4290`：

- 本仓库 `app/core/exceptions.py` 自己的码表把 **`4001` 定义为「输入内容不合规」**
  （内容审核 / 长度 / 敏感词在用）。拿它表示「今天的配图额度用完了」会让那张表变成假话。
  这与 `KNOWLEDGE_BASE_ENABLED` 那次「`.env.example` 写了没实现的语义」是同一类问题 ——
  **注释 / 文档被当成契约读，比没有更危险**。
- **`4290` 的定义就是「请求过于频繁」**（→ HTTP 429）。「每人每天 20 张」本来就是一个
  窗口为一天的限流，语义吻合。
- 前端 `ERROR_FALLBACK_TEXT` 里**没有**登记 4290，所以后端给的友好文案能原样透出。
  这一条必须查：该表里登记过的码会被前端文案**覆盖** ——
  例如 `5031` 会被改写成「当前使用的人有点多」，用户就看不出「额度用完了」。

`4001` 仍用于**开关关闭时拒绝**带 `generate_images=true` 的请求（D7）—— 那是「这个入参
在当前配置下不被接受」，且设计已按 4001 定稿。

### D6.2 原子性的实现判据（实测修正）

原设计写「`INSERT ... ON DUPLICATE KEY UPDATE` 原子自增」。但**不能拿它的受影响行数
判超额**：本机实测（pymysql，`ROW_COUNT()` 与驱动 `rowcount` 一致）——
新插入 = 1、真正更新 = 2、**命中重复键但值没变（被 `IF` 钳住）= 1**。
「新插入」与「被钳住」无法区分（官方文档说的「值未改变时为 0」在这台服务器上不成立）。

⇒ 实现取「**无条件自增 → 同一事务内回读 → 超额则把本次自增原样减回再拒绝**」。
自增是单条原子语句、直接对该行加 X 锁并持有到事务结束，回读与减回都在同一把锁下，
所以读到的一定是自己刚写进去的值，且**被拒的请求一分都不留**。

另外 `used_count` 是 `INT UNSIGNED`：退还**不能**写成 `GREATEST(used_count - N, 0)` ——
实测 MySQL 先算减法再算 `GREATEST`，减法本身已下溢报 1690。必须写成
`IF(used_count >= N, used_count - N, 0)`。两条判据都有对应用例在
`tests/test_image_quota.py` 里兜着。

## D7 开关：`IMAGE_GENERATION_ENABLED` 默认 `false`，且它是**能力**不是权限

与 `KNOWLEDGE_BASE_ENABLED` 同一条纪律（`.env.example` 注释必须描述**已实现**语义）：

- 关闭 ⇒ 前端开关不出现、后端拒绝带 `generate_images=true` 的请求（4001 友好文案）。
- 打开但缺 `dashscope_api_key` 或 COS 四项任一 ⇒ 派生属性 `image_generation_available` 为假
  ⇒ `/health` 下发 `image_generation_enabled: false` ⇒ **前端不显示开关**。
  宁可少一个入口，也不给一个点下去必然失败的按钮。
- 它**不是权限位**，但这句话**不等于「关掉也能用」**：本功能**没有独立的配额 / 生图端点**，
  请求一律走既有的 `POST /quiz/generate` + `generate_images`。开关不改变任何路由的注册状态、
  也不会 403 —— 它的真实作用是在用例层拒掉「要了配图但能力不可用」的请求（4001，见上一条）。

## D8 降级契约：生图失败**绝不**影响出题

三条硬规则：

1. 生图段的异常一律在段内兜住（与 `_gather_safely` 同构），不冒泡到 `run_quiz_generation` 的 except。
2. 单张失败 ⇒ 该题 `image_url = None`，其余题照常带图。
3. 整段失败（配额耗尽 / 上游全挂）⇒ 全部 `image_url = None`，`quiz` 照常落库、任务照常 `succeeded`。

代价是「用户勾了配图却一张没拿到」时界面不会报错 —— 这是**有意**的：需求 8 明写
「生图失败时不要影响整体出题流程」。错误只进日志与任务步骤的 `detail`（如实说「配图未生成」）。

## D9 数据层：加一列 + 建一表，DDL 幂等

- `questions.image_url VARCHAR(512) NULL`（可空 = 这道题没有配图）。
- `image_quota_usage(user_id BIGINT UNSIGNED, biz_date DATE, used_count INT UNSIGNED, 联合主键)`，
  外键指向 `users.id`（`ON DELETE CASCADE`）。
- DDL 用 `information_schema` 判断 + 预处理语句，保证**重复执行不出错**（`apply_sql.py` 逐文件跑）。
- `tests/test_db_mapping.py` 的表数 / 外键数期望值必须同步改 ——
  ⚠️ 上次加表就栽在「子集测试绿、全量红」（铁律 9）。

## D10 进度呈现：并入既有第二步，**不新增第四步**

原型「副本召唤中」是**三步**状态卡（取材 → 出题 → 校验），这是 UI 的裁决依据。生图是
「生成闯关题目」的延伸，所以写进该步的 `detail`：`已生成 5 道题 · 正在配图 3 / 5`，
并让该步的 `progress` 按完成比例在 `30 → 85` 之间推进。

好处：前端零结构改动（它本来就渲染 `detail` 字符串），原型的三步结构不被破坏。

## D11 契约：`Question.image_url`，五处自动带上

`questions` 的 `image_url` 加进对外契约 `Question`（`str | None`，默认 `None`）之后，
**轮询结果 / 确认页 / 答题页 / 复习关卡 / 历史卷轴详情**都是同一份 `Quiz` 序列化出来的，
因此五处自动带上，不需要各自加一套字段。

⚠️ 因为 `Question` 是 `extra="ignore"` 的模型，模型**有可能**自己吐一个 `image_url` 字段 ——
`draft_to_quiz` 必须**强制清空**它（配图只能由服务端生图段写入），否则会出现
「模型编了一个假图片链接」这种最难查的假数据。

## D12 与现状 / 原型的冲突点（不自行拍板，逐条给出取舍与结论）

| # | 冲突 | 处理 |
|---|---|---|
| 1 | 需求写「单次最多 6 张」+「并发调用」，两者互斥（D2） | 取「每题 1 张 + 并发」；已在上方说明，**若你更看重单次调用数，请回退此功能** |
| 2 | 原型召唤屏是**三步**，生图是第四件事 | 并入第二步 detail，不新增第四步（D10） |
| 3 | `user_settings.auto_load_images`（「流量下自动加载配图」）已存在 | **不复用、不修改**。那是「加载策略」（客户端偏好，且设置页已注明「本轮只记录回显」），本次是「生成开关」（出题参数）。两者不是一件事，合并会让「关掉生成」意外等于「不加载」 |
| 4 | `core/ratelimit.py` 现成，但语义不匹配日配额 | 新建 `image_quota_usage` 表（D6），不改既有 limiter |
| 5 | 512×512 是 z-image-turbo 的**允许下限**（上游默认 1024×1536、官方推荐区间 1024×1024–1536×1536），质量明显低于推荐区间 | 做成配置项（`IMAGE_SIZE`），默认 `512*512` 按你的方案；想提质量改 `.env` 即可，代码不动 |
| 6 | 需求 8「生图失败不影响出题」与「用户勾了却没图」的观感冲突 | 按需求 8 执行：失败静默降级，只在步骤 detail 与日志里如实说明（D8） |

## D13 对 `config.yaml` 硬约束的逐条回应

1. **后端 TDD（先测后实现）**：`tasks.md` 每条后端任务都拆成「写测试跑红」+「写实现跑绿」两步，
   生图三段与配额服务一律先写测试（上游全部用替身，不发真实请求）。
2. **前端零视觉漂移**：新增的开关是**新增控件**（不改既有控件），但大厅新增第二枚 pill
   会与既有 pill 并排 ⇒ 必须真浏览器实测 390×844 的 `getBoundingClientRect`，
   确认既有 pill 尺寸未变（`.pill` 需 `flex: none`，否则会被压扁）。
3. **密钥绝不入库**：COS 四项只写进 `.env`（`.env.example` 留空占位）；
   提交前跑 `python tools/scan_secrets.py`（`COS_SECRET_KEY` 会被扫描器识别为敏感键）。
4. **统一信封**：新入参走既有 `QuizGenerateRequest`，新下发字段走既有 `/health` 的 `ok(...)`，
   前端只在 `services/` 里解包 —— 本变更**不新增端点**。
5. **同步更新 docs 与 shared**：`docs/方案设计文档.md` 增一节；`shared/scoring-cases.json`
   与配图无关（评分不受影响），因此**不动**，在 tasks 里写明「已确认无需改」。
6. **文案与实现冲突时改文案**：配额耗尽的提示、开关的描述，都按实际能力写；
   开关不可用时**不显示**，而不是显示一个点了报错的按钮。
7. **入口一并交付**：生成设置页 + 大厅两处入口都在本次交付范围内（含导航可达性实测）。

## D14 不做的事（与 proposal 的 Non-goals 一致）

异步补图 / 尺寸风格可选 / 图床生命周期管理 / 必选化。另：**不把配图纳入「事实依据」范畴** ——
`quiz-grounding` 的规格基线一字不改，配图只是辅助记忆的视觉材料。

## D15 生图模型由 `qwen-image-2.0` 换成 `z-image-turbo`（2026-09-26）

**动机**：便宜、快，且官方写明「图像张数：**固定 1 张**」—— 与 D2 的「每题一次调用」天然契合。

**为什么不用改代码**：两者同属百炼 `MultiModalConversation` 家族
（`POST /services/aigc/multimodal-generation/generation`），`messages` 结构一致，
图片都在 `output.choices[0].message.content[0].image`。⇒ 只改 `IMAGE_MODEL` 的默认值。

**参数集差异是「实测过」的，不是推断**：z-image-turbo 官方 `parameters` 只文档化
`size` / `prompt_extend` / `seed`，而本模块**额外还发** `n` / `watermark` /
`negative_prompt` / `result_format`（第四个是取 `message` 形响应的前提）。
官方给的错误示例恰好是 `InvalidParameter: num_images_per_prompt must be 1`
⇒ **多传参数是可能 400 的**，所以按红线 7 真跑了一次：
`scripts/probe_z_image_params.py` 四种组合（含**真实提示词**那一发）**全部 200**
⇒ 多传不会打挂，参数保留不动。

| 用例 | size | 结果 | 耗时 |
|---|---|---|---|
| 仅文档内参数 | 1024*1024 | 200 | 4.12s |
| **加上我们正在发的 4 个参数** | 1024*1024 | 200 | 3.52s |
| 仅文档内参数 | 512*512 | 200 | 1.42s |
| **真实提示词**（`build_prompt` 产物，233 字符） | 512*512 | 200 | 1.44s |

⚠️ **被接受 ≠ 被采用**：`watermark` / `negative_prompt` 是否对 z-image 真正生效
**未经验证**（官方参数表里没有它们）。config / `.env.example` / 方案设计 §15 三处都按这个措辞写，
避免再出现「注释承诺了没实现的语义」（假契约，见项目铁律 10）。

**顺带查实的一点**：`prompt_extend` 在两个模型上**默认值相反**
（qwen-image-2.0 为 `true`、z-image-turbo 为 `false`）⇒ 代码必须**显式传**，
不能靠上游默认；两边官方都说明开启会增加费用。

**未验证项**（当时）：新模型的实际出图质量、以及「画面不出现文字」的达成率 ——
图片内容不可自动断言，需要人眼看图，当时**未做**。
→ 这一项在 D16 里补做了，**结论是当时的形态不达标**。

## D16 提示词形态从「规格说明书」改成「画面描述」（2026-09-26，人眼验收驱动）

**怎么发现的**：真链路跑通（3/3、回读 200）之后把图下载下来人眼看 ——
**三张全部带文字**，且是灾难性的：

| 题 | 画面里出现了什么 |
|---|---|
| 咖啡烘焙（z-image） | 标题「咖啡烘焙」+ 底部「烘**烘**焙到什么温度区间 会进第一次 **><** 爆裂」（错字 + 乱码符号） |
| TCP 协议（z-image） | 题干被当标题；错字「三次**提手**而不是两次」；底部「61」「C-」「×」 |
| 光合作用（z-image） | **我们自己提示词里的指令原文**：「固属要求：只具体、常见，容易应阶段」 |
| TCP 协议（qwen） | 完整题干 + 「所属知识点：TCP 协议」+ 一长串带图标的乱码列表 |

**根因不是模型，是提示词形态**。旧提示词是一份**给人看的规格说明书**：
分段 + `画面主题：` + `画面要求：` + `1./2./3.` 编号 + 末尾「画面中不得出现任何文字」。

**结论：提示词里任何一"条"给人看的指令，都会变成画面里的一行字。**
中文生图模型对「知识卡片」有强先验 —— 见到 `1. 2. 3.` 的排版就直接照着排版画，
连**那句禁令本身**和**冒号标签**都被渲染了出来。

⇒ 新形态：**单段、逗号分隔、无换行、无编号、无冒号标签、一句否定句都没有。**

### 另外三条实测结论（都推翻了之前的假设）

1. **「不出现文字」写进正向提示词是反效果**。禁令里的「文字」二字反而是触发词。
   现在它只在 `IMAGE_NEGATIVE_PROMPT`（生效性仍未验证）+ 风格词里兜。
   `prompt.py` 的测试也从「断言禁令在提示词里」改成「断言提示词里没有元指令」。
2. **风格尾缀必须点明「静物」**。尾缀为「写实摄影…自然光」时 z-image 把
   「光合作用」画成了**人物特写**（旧实现的「不出现人脸特写」禁令被删掉后无人拦它）。
   换成「静物摄影」→ 同一道题变成一只灯泡。`静物` 本身就排除人像，
   这是**不用否定句**达成约束的办法。
3. **拉丁字母 token 必须摘掉，但要带保护**。提示词里只要有 `TCP`，z-image
   **三次全把它画成画面正中的大字**（换尾缀也拦不住）；摘掉之后同一道题画的是
   **四端相连的接头** —— 既无文字，又真的在表达「建立连接」。

   但**无条件摘会毁掉画面**：`Python 的 GIL` + `CPython 并发` 摘完只剩「并发」，
   模型失去题材抓手后抓「静物摄影」的风格先验自由发挥，画出**一支口红**。
   ⇒ 取舍：摘完中文总量 < 6 字就整个不摘（`prompt.py::_derender_latin`）。
   代价是字母密集的题上「画面不出现任何文字」可能做不到 —— **如实登记为已知边界**。

### 换模型能解决吗？不能（实测）

| 组合（同一道 TCP 题） | 画面 | 有文字 |
|---|---|---|
| z-image + 旧尾缀 | 「TCP」大字 | ❌ |
| z-image + 静物尾缀 | 「TCP」大字 | ❌ |
| z-image + 静物尾缀 + 摘字母 | 四端接头 | ✅ |
| qwen + 静物尾缀（保留字母） | 枫叶 | ✅ |

qwen 的「没有文字」是**以彻底忽略主题为代价**的（它把「TCP 建立连接，TCP 协议」
整段丢掉了，只响应风格词）。z-image 会**试图表达主题**，代价是可能渲染字母。
⇒ 保留 `z-image-turbo`：配图要有信息量，就得留一个会尝试表达主题的模型。

### 终局验收

新形态 + 静物尾缀 + 摘字母保护，重跑 `verify_image_chain.py`：**3/3 成功、回读 200、
零 429**，人眼确认**三张全部无文字**（咖啡豆 / 四端接头 / 灯泡）。
证据 `docs/image-chain-evidence-2026-09-26.txt`。

### 仍然未验证 / 已知边界

- 抽象概念题（TCP / RAG / HTTP）的**画面相关性有限**：模型没有具体物件可画时
  会挑随机静物（花 / 叶子 / 灯泡）。这是提示词工程治不了的 —— 要治得再做一次
  「把抽象概念改写成可画物件」的 LLM 调用，超出本变更范围。
- 字母密集的题可能因保护分支而**带字母**（见上）。
- `negative_prompt` 对 z-image 是否生效仍未验证。
- 换模型 / 改风格尾缀 / 改提示词结构之后，**必须重跑人眼验收** ——
  单测只断言形态，断不了「画面里有没有文字」。

## D17 并发默认值由 `3` 下调为 `2`（2026-09-26，端到端实测驱动）

**起因**：真链路抽验时配图**成功率只有 2/3** —— 3 道题里必有 1 道拿不到图。

**实测读数**（真调百炼，非 mock；原始日志 `docs/image-chain-evidence-2026-09-26.txt`）：

| 场景 | 结果 |
| --- | --- |
| 并发 3（`verify_image_chain.py`） | 2/3，q1 返 `429 Throttling.RateQuota`（1.1s 返回） |
| 并发 3（独立复测） | 2/3，挂的同样是**第一个**请求（指纹与上一条一致） |
| 并发 3 × `qwen-image-2.0` | **2/3**，同为 429 ⇒ **不是模型的问题** |
| 并发 3 × `z-image-turbo` | 2/3，同为 429 |
| **并发 2（连跑 4 轮 / 共 8 张）** | **8/8 全过，零 429** |

**结论**：429 不是抖动，是**账号级瞬时 RPS 配额**（约 2 次/秒），且两个模型**共享同一配额**
⇒ 换模型解决不了（这一条直接证伪了「换回 `qwen-image-2.0` 就好了」的假设）。

**决策**：`image_max_workers` 默认值 `3 → 2`。理由**不是**「2 更快」，而是两条：

1. **`3` 从来没被验证过** —— 当初写下它的依据只是「与出题链共用进程，必须有界」，
   没有任何实测；而 `2` 是**真跑过 8 张零失败**的值。默认值应当来自实证。
2. 429 在 `llm/image/client.py` 里**没有重试** ⇒ 撞一次 = 那道题**没有配图**。
   降级不崩是对的，但默认配置掉 1/3 的图不可接受。

**⚠️ 别把它读成「上游硬限制是 2」**：那是**账号级配额**，别的账号可能更高。
调高之前先确认实际配额，并真跑一轮确认零 429。

**同步面**（六处，已全部改到）：`config.py` 默认值 / `.env.example` 模板值与注释 /
`conftest.TEST_ENV` 钉值 / `test_config_image.py` 断言默认值 / 本决策 / 方案设计 §15.6。

**仍未做（更根治的方向）**：429 的**指数退避重试**。降并发只是「贴着配额用」，
配额一波动照样失败；重试才是「上游忙 ⇒ 稍后重来」的正解，且能支撑更高的并发。
属独立行为变更，**不在本次范围内**。
