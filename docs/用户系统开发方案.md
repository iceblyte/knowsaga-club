## 4. 架构与技术选型

### 4.1 分层

```
小程序端                          服务端
─────────                        ─────────
Taro 4.2.1 + React 18            FastAPI 0.141.1
  ├ services/request.ts            ├ api/v1/routes/       ← 只做参数校验与响应包装
  │   token 注入 + 401 静默重登     ├ services/            ← 业务规则唯一处
  ├ store/                         ├ repositories/        ← 新增：SQLAlchemy 访问层
  │   useAuthStore（新）           ├ models/（Pydantic）  ← 请求/响应契约
  │   useUserStore（新）           ├ db/                  ← 新增：engine/session/Base
  │   useQuizStore（改）           ├ llm/                 ← chain + prompt（报告链新增）
  └ pages/…                        └ prompts/
```

**新增目录**：
- `backend/app/db/`：`base.py`（`DeclarativeBase`）、`session.py`（`create_async_engine` + `async_sessionmaker` + `get_db` 依赖）、`migrations/`（Alembic）
- `backend/app/repositories/`：每个聚合一个模块，只做 SQL，不含业务判断
- `backend/app/models/user.py`、`models/report.py`、`models/auth.py`
- `backend/app/services/auth_service.py`、`user_service.py`、`attempt_service.py`、`report_service.py`、`review_service.py`、`badge_service.py`
- `backend/app/llm/report_chain.py` + `backend/app/prompts/report_prompt.py`
- `backend/app/llm/wechat/`：`base.py`（`WechatAuthProvider` 抽象）、`real.py`、`mock.py`

### 4.2 依赖新增（实测版本，装完立刻记入 requirements.txt）

| 包 | 用途 |
|---|---|
| `sqlalchemy` 2.x | Core + ORM，`Mapped` / `mapped_column` 声明式 |
| `aiomysql` | MySQL 异步驱动（纯 Python，安装无编译风险），连接串 `mysql+aiomysql://` |
| `alembic` | 数据库迁移 |
| `pyjwt` | 签发/校验自定义登录态 |
| `cryptography` | pyjwt 的 HS256 依赖，同时为将来 session_key 加解密留口 |
| `pytest-asyncio` | 已有，异步测试 |

**不引入**：Redis（会话与任务表保持内存 + TTL，见 §6.5）、任何 ORM 之外的 DB 抽象框架。

### 4.3 为什么 `aiomysql` 而不是 `asyncmy`

`asyncmy` 更快但依赖 Cython 扩展，Windows + 本机开发环境的安装失败概率更高；`aiomysql` 纯 Python，`pip install` 必定成功。本项目的瓶颈在 LLM 调用（秒级）而非数据库（毫秒级），驱动性能差异无意义。若日后有性能诉求，换驱动**只改连接串**（`mysql+asyncmy://`），代码零改动。

## 5. 数据模型（MySQL，9 张表）

约定：所有表 `InnoDB` / `utf8mb4` / `utf8mb4_unicode_ci`；主键 `BIGINT UNSIGNED AUTO_INCREMENT`；时间列 `DATETIME(3)` 存 UTC；所有表带 `created_at` / `updated_at`。

### 5.1 `users` — 冒险者

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT PK | |
| `openid` | VARCHAR(64) UNIQUE NOT NULL | 微信唯一标识，登录凭据 |
| `unionid` | VARCHAR(64) NULL | 已绑定开放平台时才有 |
| `session_key_enc` | VARBINARY(512) NULL | 加密存储。官方红线：**绝不下发前端、绝不对外提供** |
| `nickname` | VARCHAR(32) NOT NULL | 默认「冒险者 · XXXX」（见 §9.3） |
| `avatar_key` | VARCHAR(32) NOT NULL | 预置头像键（6 选 1），未设置自定义头像时的回退 |
| `avatar_url` | VARCHAR(255) NULL | 用户上传的头像 URL，**读取时优先于 `avatar_key`**（§9.3） |
| `xp_total` | INT UNSIGNED DEFAULT 0 | 累计经验值 |
| `coins` | INT UNSIGNED DEFAULT 0 | 冒险金币 |
| `streak_days` | INT UNSIGNED DEFAULT 0 | 当前连续天数 |
| `longest_streak` | INT UNSIGNED DEFAULT 0 | 历史最长连续 |
| `last_active_date` | DATE NULL | 用于算连续天数 |
| `created_at` / `updated_at` / `last_login_at` | DATETIME(3) | |

索引：`uk_openid`、`idx_unionid`、`idx_last_active_date`。

### 5.2 `user_settings` — 设置（1:1）

| 列 | 说明 |
|---|---|
| `reminder_enabled` | 每日学习提醒开关，默认 `1` |
| `reminder_time` | `TIME`，默认 `20:00:00`（覆盖下班后学习高峰） |
| `reminder_days` | `JSON`，如 `[1,2,3,4,5]`，1=周一 |
| `remind_streak_break` | 连续记录即将中断时提醒，默认 `1` |
| `remind_review_due` | 旧识重温到期时提醒，默认 `1` |
| `sound_enabled` | 音效与振动，默认 `1` |
| `auto_load_images` | 流量下自动加载配图，默认 `0` |
| `eye_care` | 护眼模式，默认 `0` |
| `subscribe_quota` | 订阅消息剩余可下发次数（用户每授权一次 +1，下发一次 −1） |

### 5.3 `quizzes` — 卷轴

| 列 | 说明 |
|---|---|
| `user_id` | 归属冒险者 |
| `title` / `summary` / `source_type` / `source_name` | 卷轴元信息 |
| `source_hash` | 资料指纹，用于「同资料不重复建卷轴」 |
| `question_count` / `difficulty` | 生成参数 |
| `status` | `ready`（生成完成即落库；无中间态） |

### 5.4 `questions` — 题目快照

| 列 | 说明 |
|---|---|
| `quiz_id` | FK |
| `seq` | 题序（1 起） |
| `type` | `single` / `multiple` / `judge` |
| `stem` / `options`(JSON) / `answer`(JSON) / `explanation` | 与 `models/quiz.py` 的 `Question` 一一对应 |
| `knowledge_point` / `difficulty` | 报告与知识树的聚合依据 |

**为什么快照而不只存 quiz_id**：题目是 LLM 生成物，没有稳定外部 ID。历史卷轴要能无限期回看逐题内容与解析，快照是唯一可靠做法。

### 5.5 `attempts` — 一次挑战（原型「一份卷轴」）

| 列 | 说明 |
|---|---|
| `user_id` / `quiz_id` | FK |
| `attempt_no` | 该卷轴的尝试序号（首次=1） |
| `started_at` / `finished_at` / `duration_ms` | 用时 |
| `correct_count` / `wrong_count` / `partial_count` / `total_count` | 逐题统计（多选题的部分正确**不计入 correct**，与原型「4 / 5」口径一致） |
| `accuracy` | 0–100 整数 |
| `max_xp` / `xp_gained` / `coins_gained` | 得分 |
| `percentile` | `clamp(round(accuracy × 0.9), 5, 95)` |
| `avg_seconds_per_question` | 数据看板「平均单局用时」 |
| `status` | `finished` |

**口径裁决**：原型 04·第 5 屏「历史卷轴」每条显示「正确率 80% · 5 题」+ 详情页开「重做」按钮 → 列表项 = **一次 attempt**，不是卷轴。个人中心「闯关副本 12」与「历史卷轴 12」数字一致，进一步印证这个口径。同一卷轴可产生多条记录。

### 5.6 `answers` — 逐题作答

| 列 | 说明 |
|---|---|
| `attempt_id` / `question_id` | FK |
| `selected` | `JSON`，用户选中的选项键数组 |
| `outcome` | `correct` / `partial` / `wrong` |
| `earned_xp` / `max_xp` | 该题得分 |
| `time_spent_ms` | 单题用时 |
| `answered_at` | |

### 5.7 `reports` — 冒险日志（1:1 于 attempt）

| 列 | 说明 |
|---|---|
| `attempt_id` UNIQUE / `user_id` | FK |
| `status` | `pending` / `ready` / `failed` |
| `summary_lines` | `JSON`，三句话总结（恰好 3 条） |
| `strong_points` / `weak_points` | `JSON`，知识点标签数组 |
| `suggestions` | `JSON`，三条建议，每条含 `{title, body, action}` |
| `model` / `error_code` / `error_message` | 可观测性 |
| `generated_at` | |

**为什么独立表而不挂在 `attempts` 上**：报告是**异步生成**且**可独立失败**。挂在一起会让「答题记录（必须成功）」与「AI 报告（可能失败）」的生命周期纠缠——而原型 03·第 6 屏明确要求「报告生成失败时答题记录不丢失」。

### 5.8 `wrong_questions` — 错题本

| 列 | 说明 |
|---|---|
| `user_id` / `question_id` | FK，联合唯一 |
| `wrong_count` | 累计答错次数 |
| `stage` | 复习阶段 0–5 |
| `next_review_at` | 下次到期时刻 |
| `last_review_at` / `last_wrong_at` | |
| `mastered` | 连续两次复习答对 → `1`，移出队列 |

### 5.9 `user_knowledge_stats` — 知识树聚合

| 列 | 说明 |
|---|---|
| `user_id` / `kp_name` | 联合唯一 |
| `total_count` / `correct_count` | 该知识点下的题量统计 |
| `mastery` | `round(correct_count / total_count × 100)` |
| `lit` | `mastery >= 90` 时置 1（点亮阈值见 §9.5） |
| `first_seen_at` / `last_seen_at` | |

**为什么物化而不实时聚合**：知识树的树形图与数据看板的「各知识领域掌握度」都要读它；实时聚合要跨 `answers → questions` 两表按 `knowledge_point` 分组，随数据增长会变成最慢的查询。写入时机只有一处（提交 attempt），成本可忽略。

### 5.10 勋章：**不建表**

18 枚勋章的定义放 `backend/app/services/badge_service.py` 的常量注册表（`key / name / desc / icon / 条件函数`）。理由：勋章规则需要**代码表达**（如「单局满分且平均每题 <5 秒」），塞进表里只能存字符串再解释，反而引入一套 DSL。用户解锁记录走 `user_badges`（`user_id` / `badge_key` / `unlocked_at` / `progress_snapshot`，联合唯一）。

> 副作用：新增勋章 = 改代码 + 发版。对本项目（单人开发、勋章集稳定）是合适的取舍；若日后要做运营侧动态配勋章，再迁表。

### 6.4 结算为什么必须搬到服务端

现状：前端 `scoring.ts` 本地判题 + 本地算 XP。**这个架构与用户系统不相容**——前端上报什么，服务端就只能信什么，档案里的等级、累计 XP、正确率全部可被篡改；反之若服务端不复核，数据看板画出来的图就没有权威来源。

改造方式（**页面视觉与交互完全不变**）：
1. 答题过程仍在前端即时判题（保证「答对后立刻变绿」不被网络延迟绑架，这条原有决策保留）。
2. 交卷时把**逐题选择**提交后端，由服务端用 `questions` 快照重新判定并计算总分。
3. 结算页展示的数字以**服务端返回为准**；前端 `scoring.ts` 降级为「即时反馈用」，并在进入结算页时用服务端结果覆盖。
4. 服务端计算规则与 `scoring.ts` **逐条对齐**（同一套规则两处实现），并用一组用例锁定两边结果一致。

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/reports/generate` | body `{attempt_id}` → 异步任务，返回 `{task_id}` |
| GET | `/reports/tasks/{task_id}` | 轮询（复用既有 `tasks` 契约与 `to_payload` 的固定键集合） |
| GET | `/reports/{attempt_id}` | 读报告 |
| POST | `/reports/{attempt_id}/regenerate` | 重新生成（对应原型 03·第 6 屏「重新生成报告」） |

**报告任务保持进程内内存 + TTL，不落库。** 理由：任务是**过程态**（用户盯着进度条等十几秒），而报告是**结果态**（落 `reports` 表）。进程重启后未完成的任务消失，`reports` 行仍为 `pending` → 前端点「重新生成报告」即可恢复。这既保留了既有 `task_service` 的简洁，又不会造成数据丢失。

## 9. 规则定义与待确认细节

### 9.1 登录与开发通道

**生产路径**（小程序）：
```
Taro.login() → code(5 分钟有效, 一次性)
  → POST /auth/wechat {code}
  → GET https://api.weixin.qq.com/sns/jscode2session
       ?appid=&secret=&js_code=&grant_type=authorization_code
  → {openid, session_key, unionid, errcode, errmsg}
  → upsert users → 签发 JWT(HS256, sub=user_id, exp=30d)
  → {token, user}
```
- `session_key` **加密存库，绝不下发前端**（官方明文要求）。
- JWT 存 `Taro.setStorageSync('ks_token')`；请求头 `Authorization: Bearer <token>`。
- `request.ts` 加 401 拦截：自动静默重登一次，失败才跳登录。

**阻塞（需要你提供）**：正式小程序 **AppID + AppSecret**。当前 `project.config.json` 的 `appid` 是 `touristappid`（测试号），**测试号无法调用 `code2session`**，拿不到 openid，微信登录路径一行都跑不通。

**H5/本机联调通道（已确认接受）**：`DEV_LOGIN_ENABLED=true` 时额外挂一个 `POST /auth/dev {device_id}`，按 `device_id` 派生稳定 openid。H5 端自动走它，小程序端走真登录。生产 `.env` 置 `false`，该路由**不注册**（不是注册了再拒绝）。
> 这不是新增一种登录方式，而是一条本地调试旁路——否则我无法在本机验证除登录外的任何一条链路。

### 9.4 等级曲线（**能精确对上原型数字**）

```
threshold(1) = 0
threshold(n) = 400 + 800 × (n − 2)     (n ≥ 2)
→ 0, 400, 1200, 2000, 2800, 3600 …
```
验算原型：`Lv.3` 区间 `[1200, 2000)`，用户 1280 XP → 本级进度 `1280 / 2000`，「距离 Lv.4 还差 720」→ `2000 − 1280 = 720` ✓ 完全吻合。
头衔随等级：`见习冒险者`(1–2) → `初级冒险者`(3–4) → `资深冒险者`(5–6) → `史诗冒险者`(7–8) → `传说冒险者`(9+)。（原型只出现「见习冒险者」，其余为自拟）

**原型内部有一处数字冲突**（请你裁决）：04·第 1 屏上方进度条写 `1280 / 2000`，同屏三宫格又写「累计 XP **1840**」。二者不可能同时成立。
**我的裁决**：统一为「累计 XP / 下一级门槛」，即进度条 `1280 / 2000`、三宫格「累计 XP **1280**」。理由是进度条的分母必须是下一级门槛才能让「还差 720」成立；三宫格那个 1840 是孤立的演示值。

### 9.5 知识树点亮阈值（自拟，需确认）

`mastery = round(correct_count / total_count × 100)`，`mastery ≥ 90` → 点亮 `lit=1`。
验算原型：`AI 基础 92% → 已点亮` ✓；`RAG 80% → 进行中` ✓；`评测 0% → 未开始` ✓（`total_count = 0` 时状态为「未开始」，注意 0 不能落进「进行中」）。

### 9.6 错题复习间隔（自拟，即原型说的「艾宾浩斯遗忘曲线」）

```
stage:      0    1    2    3    4    5
间隔(天):    1    2    4    7    15   30
```
- 答错 → `wrong_count + 1`，`stage` **回到 0**，`next_review_at = now + 1 天`。
- 复习答对 → `stage + 1`，`next_review_at = now + 间隔[stage]`。
- 连续两次复习答对 → `mastered = 1`，移出队列。
- 原型验算：「答错 1 次 · 今天到期」「答错 1 次 · 3 天后」——「3 天后」需 `stage=2`（4 天）或 `stage=1`（2 天）都不精确等于 3；原型是演示文案。**按上表实现，不用 3 这个数。**

- 后端严格 **TDD**：每个 service 先写红测试再写实现。
- **LLM 与微信接口一律 mock**，pytest 中不发任何真实外部请求。
- 数据库测试跑在**独立测试库**上；每个测试用例后清表。
- 前端每屏完成后做 **DOM 实测**（`getBoundingClientRect` + `getAttribute('style')`），不靠肉眼看截图——本项目已有三条「静默失效」的教训（自定义元素丢 `style` 对象、内联 `rpx` 被丢弃、`statusBarHeight` 返回 `NaN`）。
- 结算规则用**共享用例表**锁定前后端一致（同一组输入 → 同一组输出）。

## 12. 风险与对策

| 风险 | 对策 |
|---|---|
| 测试号无法登录，登录链路无法自测 | §9.1 的 dev 旁路 + 你提供正式 AppID 后真机验证 |
| H5 与小程序行为差异（storage / login / canvas） | 平台差异一律收敛到 `utils/` 的单一分支，不在页面里散写 `if (process.env.TARO_ENV)` |
| 报告异步任务进程重启丢失 | 任务不落库但报告落库（§6.5），前端「重新生成报告」可恢复 |
| MySQL 迁移不可回滚 | 每个 Alembic revision 都写 `downgrade()` 并单测验证 |
| 前后端算分规则漂移 | 共享用例表 + 单测双向锁定（§11） |
| 历史卷轴数据量增长后列表变慢 | `attempts` 建 `idx_user_created` 复合索引；分页 20 条 |
