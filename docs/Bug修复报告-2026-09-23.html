1社团大厅的搜索框超出边界，盖住下方「热门问题」

现象
大厅中间的木质卷轴输入框超出了它自己的边界，里面的文字与「AI 将联网补充」胶囊画到框外，压住了下面「热门问题」那一行。
根因
不是「谁把高度写错了」，而是溢出没人管。 .hall__input 原本写的是 flex: 1，展开是 1 1 0%——收缩系数是 1，可被压缩。 容器一被压，卷轴框就缩到只剩 padding（实测 37.4px）；而框内那层虚线内容区是 min-height:100% + 高度 auto， 它按自己的 min-content 长到 101px，直接画到框外；外层 .screen--static 又是 overflow: visible，不裁切。 于是溢出的内容（含那枚联网胶囊与「13 / 200」）就盖在了下方的「热门问题」上。
改了什么
① .hall__input 改成 flex: 1 0 auto——只长不缩，空间不够时保持内容高度，把下移交给滚动，不存在第三种画法。 ② 给 .hall__textarea 写死两行行高（height: 44rpx）。这条是必要的：不写它时 flex-basis:auto 会去问平台「这个 textarea 自然多高」， H5 给 40px、微信原生组件给的是另一个值——上面那条「按内容高度兜底」的基准会随平台漂移，等于没兜住。
实测证据
在同一个页面、同一份构建上做 A/B：把 .hall__input 的 flex 内联改回旧写法 1 1 0% 现场复现，再改回来。 读数（390 × 600）如下——「内层底边 vs 热门问题」为正数即表示压住了。

没有回退既有观感：在原型基准视口 390×844 下实测框高 194.5px，与修复前逐位相同—— 这次改的是「空间不够时怎么办」，空间够的场景一个像素都没动。

2看不到「联网搜索」按钮

现象
大厅里找不到联网搜索的开关，怀疑被别的东西盖住了。
根因
两个成因叠在一起，必须分开说：
  • 一半是被盖住：那枚「AI 将联网补充」胶囊恰好坐在 Bug 1 的溢出区里，被下方的「热门问题」压住了——所以看不见，也点不到。
  • 一半是设计如此：它只在输入框有内容之后才出现（hasInput 为真时渲染）。空态大厅本来就没有这枚胶囊，没有输入时找它当然找不到。
把「看不见」一句话说成「修好了」，就会漏掉第二种情况：用户下次空着输入框再找一次，还是会以为丢了。
改了什么
只修被盖住的那一半（即 Bug 1 的溢出）。胶囊自身的渲染条件保持不变—— 有输入才出现是原型的「已输入态」，是产品设计，不是缺陷，因此没有动它。
实测证据

「可见」之外还要「能点」：在 390×600 压力视口下真点一次，文案随点击切换—— AI 将联网补充（pill blue）→ 基于已有知识出题（pill）→ 再点回 AI 将联网补充。 截图里能看到它正落在卷轴框内部。

3「百分位为演示数据，不是真实统计」不适合给用户看

现象
冒险日志页的百分位卡上挂着一句「（演示数据）」。分数单上印这句话，等于当着用户的面承认数字是编的。
根因
它当时确实是编的：clamp(round(accuracy × 0.9), 5, 95)——正确率的单调映射， 没有用户池、没有比较，只是把正确率换个刻度显示。所以那句标注是诚实的， 但「诚实地展示一个假数字」本身就是产品问题，正确解法是把数字做成真的。
改了什么
百分位从「正确率的派生值」换成 真实社团分位：
  • 口径：本局正确率严格高于社团里其他冒险者「最佳正确率」的人数占比。 池子为空时返回 None——界面不显示任何百分数（显示 0% 会被读成「谁也没超过」，而真相是「还没有人可比」）。
  • 落点：新增 backend/app/services/percentile_service.py 与 scoring.pool_percentile； attempts 表新增 percentile_pool 列（幂等迁移 sql/05_attempts_percentile_pool.sql）。
  • 前端不再自己算：删掉本地镜像实现 percentileOf，结算页与报告页那一格只认服务端—— 前端手里没有别人的成绩，算了也是错的。
  • 存量回算：scripts/backfill_percentile.py 把历史 25 条按新口径重算（其中 1 条数值变化）， 复查输出「需改 0 条」= 幂等。
  • 文案：删掉「（演示数据）」；报告页补上一句「按社团里 N 位冒险者的最佳正确率计算」—— 只说「超过 14%」时，用户没法判断这 14% 是在 3 个人里排的还是 300 个人里排的。
实测证据（本轮重新跑了一遍完整链路，不是沿用上一轮）
  • 端到端：大厅输入「什么是 RAG 检索增强，它的原理是什么」→ 召唤 → 答对 1/5 → 结算页「超过社团里 14% 的冒险者」→ 冒险日志页「本局超过社团里 14% 的冒险者」+ 胶囊「起步」+ 进度条 14% +「按社团里 7 位冒险者的最佳正确率计算」。
  • 界面上再无那句免责声明：整页 document.body.innerText 里搜「演示数据」= false。
  • 库里重算对得上：attempt 30 → accuracy 20，落库 14，重算 14，pool 7，matches: true； 最近 5 条记录全部 true。
  • 14 这个数可以手工验算：社团 8 人，除本人外 7 位的最佳正确率为 0 / 20 / 80 / 100 / 100 / 100 / 100， 严格低于 20 的只有 1 人 → 1 ÷ 7 = 14.3% → 14。数字对得上，不是随手编的。
顺手发现的一处服务端事故（已修，但值得记一笔）： 验证时发现 8000 端口上跑着的后端进程是改动前启动的（12:44），它按旧口径往库里写了一条记录 （attempt 28：accuracy 40 → 旧公式给出 36，且 percentile_pool = 0）。 重启到新代码后回算修正为 29，并已逐条核对通过。 这条不算产品 Bug，但说明一件事：改完算法必须重启服务再验收，否则界面会拿旧口径的存量数据糊弄你。

附加发现：百分位卡的档位胶囊被挤成两行（既有视觉缺陷，已一并修掉）

这不是本次 3 条里的任何一条，也不是本次改动引入的——是在给 Bug 3 截图量尺寸时量出来的。

现象：百分位卡右上角的档位胶囊「起步」竖着排成了「起 / 步」两行，看着像坏了。

根因：基座的 .pill 是 flex: 0 1 auto（可缩）， 而这一行左边是「本局超过社团里 14% 的冒险者」这种会长成两行的标题——标题一占满，胶囊就被压到 39.5px， 而它自己需要 41px，两个字只好换行。

为什么算「既有」：标题文案与胶囊文案这次都没动（档位一直是那 5 个两字词：起步 / 中游 / 中上 / 优秀 / 顶尖）， git diff 可证本次只改了这一个分支的结构，没改这一行的排版属性。

修法（小范围）：只在这张卡内部加一条 .report__percentile .pill { flex: none }， 与同一文件里已有的 .report__note { flex: none } 是同一个理由。 没有去动基座 .pill——那是全站共用的，改了会漏到别的页面，那就越界了。

实测：39.5 × 45.1（两行，flex: 0 1 auto）→ 41.0 × 25.1（一行，flex: 0 0 auto）。

4「热门问题」chip 点一下就直接召唤副本（应改为填进输入框）

现象
大厅空态下方那一排「热门问题」，点一下直接跳到召唤页开始出题。 用户只是想少敲几个字，却被替按下了「开始」——一次召唤是有代价的动作，不该由 chip 代拍板。
根因
这条不是「一直写错了」，而是被改反过一次：
  • 最初实现本来就是「点一下只填进输入框」。
  • 但当时收到的反馈是「点了一点反应都没有」——填字这个动作在视觉上太轻（输入框里多一行字）， 用户以为 chip 是坏的，于是被改成了「点一下直接召唤」。
  • 两端的诉求其实是同一个（别让用户觉得白点了），但当时选错了补偿方式： 跳过了用户的确认环节。正确解法是把后果写进文案，而不是替用户把按钮按下去。
所以本轮不是简单回退，而是「恢复只填不发 ＋ 补一句说明」一起做。 这段双向历史已经写进 hall/index.tsx 文件头注释，免得下一个人只看代码、以为是漏写的 bug 又改回去。
改了什么
  • summonWithPreset() → fillPreset()：删掉 goPage('/pages/summon/index','navigate')， 只留 setDraft(question) ＋ setUserInput(question)——只填，不跳。 于是下方「召唤副本」的 canSubmit 与 8 字下限照旧生效，用户还有机会改几个字再发。
  • 标签文案：热门问题 · 点一下直接召唤副本 → 热门问题。 当天一度补过后半句「· 点一下填进输入框」，随后按用户要求删掉，最终只留「热门问题」三个字 —— 也就是说，现在界面上不再解释点击后果，那点「点了没反应」的观感风险是 知情接受的（理由与边界见节末提示）。
  • 顺手补一处同源隐患：onInput 现在也把内容 setUserInput 镜像进 store。 大厅是标签页（切走不卸载），useDidShow 会执行 setDraft(store.userInput) 把输入框重置回 store——此前只写本地 draft，用户手打的字切一次标签页就被擦掉了， 表现和「点了没反应」一模一样。

附录 A · 联网搜索真实性验证

你点名要先测这条。结论：真实联网，从服务端日志、数据库落库、端到端三条线交叉确认。

A1 · 端到端真的调了外部检索

本轮重新生成一份副本：大厅输入中文题目「什么是 RAG 检索增强，它的原理是什么」，联网开关置为 ON。 服务端日志（app.llm.search.agent）实录：

取材结束：provider=tavily reason=done rounds=2 calls=1 hits=5

读法：provider 是 Tavily；有界 Agent 循环跑了 2 轮后自行判定「够了」（reason=done）； 向检索服务发出 1 次调用；拿到 5 条命中。紧接着出题链第 1 次尝试即成功、题量 5。

  • 更早的 quiz #49 / #50：含 kind=page（按网址读整页），单条最长正文 6007 字符—— 说明「读整页」这条路径也真的走通过，不只是拿搜索摘要。
  • 全库带 http URL 的参考来源共 74 条。

A3 · 为什么这不是「假联网」

  • 出题链吃的就是检索回来的资料快照——source=web 的条目带 URL 与正文片段，它们和题目一起落库， 可逐条回查；不是「调了个接口然后丢掉结果」。
  • degraded 这一态的存在本身就是证据：如果代码只是走个过场假装联网， 就不会出现「调了但失败、于是明确降级」这种第三种状态。
  • 中文查询也能命中：本轮与上一轮的中文题目都拿到了中英文来源，说明不是「只对英文有效」。
一句话总结：联网检索是真的——它真的出网、真的把结果写进了库里、真的参与了出题； 失败时也真的会降级并如实标记，而不是编一份看起来很联网的题。
