## 1. 与「小程序用户系统标准做法」的对齐审计

项目是否采用**微信静默登录 + JWT 鉴权**这一标准做法。以下结论基于**代码实测**与微信官方文档，不是推测。

### 1.1 先澄清一个前提

**审计对象不是「已有实现」，而是「已有的开发方案」。** 实测结论：全仓 grep `openid` / `jwt` / `Authorization` / `token`，除 LLM 的 token 计数外**零命中**——项目此前没有任何一行用户系统代码。所以这里不存在「现有代码不符合标准」，只存在「既有方案文本与标准的偏差」。

### 1.2 标准做法的七个要素

| # | 要素 | 标准做法 |
|---|---|---|
| S1 | 登录方式 | `wx.login()` **静默**获取临时凭证 `code`（无授权弹窗、无用户操作）。需要用户点击授权的只有头像/手机号等能力，与登录分离 |
| S2 | 凭证校验 | `code` 只能由**服务端**调 `code2Session` 换取身份（`GET https://api.weixin.qq.com/sns/jscode2session?appid=&secret=&js_code=&grant_type=authorization_code`），**不可在前端调用**（官方明文要求，且前端没有 secret）。`code` 一次性、5 分钟有效 |
| S3 | 登录态 | 官方推荐「**自定义登录态**」：服务端签发自有凭证，前端持久保存，后续请求随头部携带 |
| S4 | 会话密钥 | `session_key` **必须保密**（用于解密敏感数据与校验签名），绝不下发前端 |
| S5 | 有效期与续期 | 登录态必须有过期；过期后应能**静默重建**（因为 `wx.login` 本身是静默的，重建成本 ≈ 一次请求） |
| S6 | 接口鉴权 | 除明确的白名单外，全部接口需要身份；**按 id 取数据必须校验归属**（防横向越权） |
| S7 | 隐私合规 | 处理用户信息前需在管理后台配置《小程序用户隐私保护指引》并同步用户同意状态，否则相关能力被平台禁用 |

### 1.3 逐条判定

| # | 原方案的做法 | 判定 | 本次设计 |
|---|---|---|---|
| S1 | `wx.login → code2session → openid` | ✅ **符合** | 沿用。全流程无弹窗 |
| S2 | 服务端调 `code2session`，参数 `appid/secret/js_code/grant_type` | ✅ **符合** | 沿用，并按官方错误码分别映射（§4.4） |
| S3 | 「后端签发自定义登录态」，形态是 `JWT(HS256, sub=user_id, exp=30d)` | ✅ **方向符合** | 明确为 JWT，并把算法、密钥强度、载荷字段写死（§4.1） |
| S4 | `session_key` 加密存库，不下发前端 | ⚠️ **偏离**：存了却没有任何使用场景 | **本轮不落库**（§5.1）。不存即无泄漏面；将来真要用再加一列迁移 |
| S5 | 单一 30 天 token，无撤销机制 | ⚠️ **缺口** | 7 天有效期 + 版本号撤销 + 失效静默重建 + 并发去重（§4.2） |
| S6 | 只给 `/users/*` 等**新**接口加鉴权，未提及既有 `quiz.generate` / `tasks.*` | ⚠️ **缺口**：既有接口匿名，且任务无归属，可跨用户读任务 | 补**接口鉴权矩阵**（§4.3），既有接口一并纳入 |
| S7 | 未提及 | ⚠️ **缺口**：不配置会导致 `chooseAvatar` / 昵称输入被禁用或**静默降级** | 纳入 FR-A7，见 §7.4 |

### 1.4 另发现的六处偏差（与「标准」无关，但会直接导致线上问题）

| # | 偏差 | 证据 | 修正 |
|---|---|---|---|
| D1 | 表排序规则写 `utf8mb4_unicode_ci` | 本机实测 MySQL **9.0.1** 服务端为 `utf8mb4` / `utf8mb4_0900_ai_ci`；库表与连接不一致时，跨表 JOIN 会报 `Illegal mix of collations` | 统一 `utf8mb4_0900_ai_ci`（§2.2） |
| D2 | 依赖表把 `cryptography` 标为「HS256 依赖 / 未来留口」 | MySQL **9.0 已移除** `mysql_native_password`；实测本机账号插件为 `caching_sha2_password`（§2.2）。异步驱动做完整认证**必须**有 `cryptography` | 提升为**必需依赖** |
| D3 | 「9 张表」 | 原文档正文实际列出 10 张（含勋章记录表） | 更正为 **10 张表**（§5） |
| D4 | 「改造页（2）」 | 正文实际列出 3 个页面 | 更正为 **改造 3 页**（§7.3） |
| D5 | 无防重复提交设计 | 交卷是客户端重试概率最高的请求，重复上报会产生重复挑战记录，污染统计 | 增加一次性交卷令牌（§5.5 `client_token`） |
| D6 | 无时区口径 | 「今天」「连续天数」「错题到期」都依赖「今天」的定义；数据库存 UTC 时若按 UTC 判日，晚上 8 点后学的会被算到第二天 | 固定业务时区 `Asia/Shanghai`（§8.7） |

### 1.5 结论

**方案骨架与标准做法一致**（静默登录 + 服务端换身份 + 服务端签发自有登录态），本次**不推翻**，但需按 §1.3 的 4 处缺口与 §1.4 的 6 处偏差补齐——其中 **S6（既有接口纳入鉴权 + 归属校验）** 与 **D1/D2（数据库事实）** 是必须改的，否则会出现越权读取与联调跑不起来。

> 「静默」的准确含义：`wx.login()` 本身不弹授权框，所以登录可以全自动。真正需要用户授权的是**头像昵称**（原型外的 `pages/settings/profile` 一页），它不在登录链路上。

### 2.3 为什么是 `aiomysql` 而不是 `asyncmy`

`asyncmy` 更快，但依赖 Cython 扩展，Windows 本机安装失败概率更高；`aiomysql` 是纯 Python（底层 PyMySQL），实测一次装通。本项目瓶颈在 LLM 调用（秒级）而非数据库（毫秒级）。若将来有性能诉求，**只改连接串**即可切换，代码零改动。

### 2.4 本机开发环境的一个已解决问题（仅影响开发过程，不影响交付物）

沙箱内 `pip` 访问包索引会被拦截（返回「无可用版本」），但 Python 直连索引是通的（HTTP 200）。**已验证的绕行方式**：直接用 Python 下载 wheel 到本地目录，再用 `pip install --no-index --find-links=<目录>` 安装。此方式纯本地解析，不依赖索引，已在本次审计中跑通。

## 4. 鉴权设计（登录态全生命周期）

### 4.1 登录态规格（JWT）

| 项 | 取值 | 说明 |
|---|---|---|
| 算法 | `HS256` | 校验时必须显式传 `algorithms=["HS256"]`，**不接受**由 token 头部指定算法（防算法混淆/`alg=none`） |
| 密钥 | `JWT_SECRET`，≥ 32 字符随机 | **必填**。缺失或过短时服务**启动即失败**，绝不用默认值兜底 |
| 有效期 | `JWT_EXPIRE_HOURS=168`（7 天） | 见 §4.2 |
| 载荷 | `sub`（用户 id 字符串）、`ver`（版本号）、`iat`、`exp`、`jti` | `ver` 用于服务端主动失效（§4.5） |
| 传输 | 请求头 `Authorization: Bearer <token>` | 不用 Cookie（小程序无此能力，H5 亦跨域） |
| 存放 | 客户端本地持久存储（`Taro.setStorageSync('ks_token')`） | 小程序端与 H5 端行为一致 |

**校验顺序**（任一失败 → 401）：签名 → `exp` → `sub` 可解析为整数 → 用户存在 → `ver` 与库中一致。

### 4.2 为什么是「7 天 + 静默重建」而不是「refresh token 双令牌」

`wx.login` 是静默的，**重建一个登录态的成本就是一次 HTTP 请求**（小程序端 + 服务端各一次）。这比维护 access/refresh 双令牌、轮换、并发续期竞态要简单得多，而且每次重建都会重新走一次官方凭证校验，安全性不低于 refresh 方案。

- 有效期 7 天，覆盖「一周回来一次」的典型回访节奏。
- 到期或失效 → 前端自动重建，用户无感（§4.4）。
- 只有一种令牌，不存在「refresh 泄漏 = 无限续期」的问题。

> 若将来需要「同一用户多设备分别管理」，再引入令牌表；本轮单端场景不做，避免过度设计。

### 4.3 接口鉴权矩阵（**本节修正了原方案 S6 缺口**）

| 方法 | 路径 | 鉴权 | 归属校验 |
|---|---|---|---|
| GET | `/api/v1/health` | 免 | — |
| POST | `/api/v1/auth/wechat` | 免（本身是登录） | — |
| POST | `/api/v1/auth/dev` | 免，**仅开发环境注册** | — |
| POST | `/api/v1/auth/logout` | 必须 | — |
| POST | `/api/v1/quiz/generate` | **必须**（新增） | 卷轴归属当前用户 |
| GET | `/api/v1/tasks/{task_id}` | **必须**（新增） | **任务归属当前用户**，否则按「不存在」处理 |
| POST | `/api/v1/tasks/{task_id}/cancel` | **必须**（新增） | 同上 |
| POST | `/api/v1/attempts` | 必须 | 卷轴必须属于当前用户 |
| GET/POST | `/api/v1/reports/*` | 必须 | 报告归属当前用户 |
| GET/PATCH | `/api/v1/users/me*` | 必须 | 只操作自己 |
| GET | `/static/avatars/{file}` | 免 | 文件名由服务端生成且不可枚举 |

**要点**：越权与「不存在」返回**同一个结果**，不泄漏「这条数据存在但不属于你」。

### 4.4 登录时序

**首次进入 / 无登录态**

```
splash 启动
 └─ 读取本地登录态
     ├─ 无 → wx.login() 取 code → POST /auth/wechat {code}
     │        → 服务端 code2Session → openid → 建档或查档 → 签发 JWT
     │        → {token, expires_in, user} → 本地保存 → 进入大厅
     └─ 有 → GET /users/me 探活
              ├─ 成功 → 用返回值填充界面 → 进入大厅
              └─ 401  → 静默重建（同上）→ 成功则继续；失败才提示
```

**运行期失效（自动恢复）**

```
任意请求 → 401
 └─ 拦截器：是否已有重建在飞？
     ├─ 有 → 挂起等待同一个重建结果（单飞，避免并发多次登录）
     └─ 无 → 发起重建 → 成功 → 用新登录态重放原请求（每个请求最多重放 1 次）
                       → 失败 → 清本地登录态 → 回启动页并给出可理解提示
```

**防死循环**：重放出去的请求不再触发重建；单次会话连续重建失败 ≥ 2 次即停止自动恢复。

### 4.5 登出与主动失效

- `POST /auth/logout` → 服务端把该用户的 `token_version + 1` → 旧登录态立即全部失效（§5.1）。
- 前端清本地登录态并回启动页。
- 代价：递增一列，鉴权时本来就要查一次用户行，**几乎零额外成本**；好处是「登出」从假动作变成真动作。

### 4.6 错误码与 HTTP 状态

沿用既有的 `{code, message, data}` 统一响应，但**HTTP 状态码必须同时正确**（否则前端拦截器与网关都难以判断）。

| 业务码 | HTTP | 含义 | 触发场景 |
|---|---|---|---|
| `4010` | 401 | 未登录或登录态无效 | 无 token / 格式错 / 签名错 / 过期 / 版本号不匹配 |
| `4011` | 401 | 微信登录凭证无效或已被使用 | `code2session` 返回 `40029` |
| `4030` | 403 | 账号被限制登录 | `code2session` 返回 `40226` |
| `4002` | 400 | 上传文件不合规 | 头像类型/大小/内容校验失败 |
| `4005` | 404 | 资源不存在或无权访问 | 越权访问他人卷轴/报告/任务 |
| `4290` | 429 | 请求过于频繁 | 登录接口限流 / `code2session` 返回 `45011` |
| `5032` | 502 | 微信接口调用异常 | `code2session` 返回 `-1`（系统繁忙）或网络异常 |

既有码（`4000` 参数、`4001` 内容不合规、`4004` 任务不存在、`4090` 任务不可取消、`5000`/`5001`/`5030`/`5031` AI 相关）**不变**；昵称不合规复用 `4001`。

### 4.7 开发调试通道的边界

- 仅在 **同时满足**「运行环境为开发」**且**「显式开启该开关」时**注册**该路由；不满足时该路径**根本不存在**（返回 404，而不是「已注册但拒绝」）。
- 它按本地设备标识派生一个稳定身份，用于 H5 与本机联调——否则除登录外的任何链路都无法在本机验证。
- 生产配置下该路由不存在，因此不存在「忘记关掉」的风险面。

## 5. 数据模型（MySQL，**10 张表**）

### 5.0 全局约定

| 项 | 约定 |
|---|---|
| 建库 | `DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci` |
| 表 | `ENGINE=InnoDB`，同库同排序规则 |
| 命名 | 全小写 `snake_case`（因 `lower_case_table_names=1`，且保证迁 Linux 可用） |
| 主键 | `BIGINT UNSIGNED AUTO_INCREMENT` |
| 时间 | `DATETIME(3)`，**存 UTC**；「业务日期」按 `Asia/Shanghai` 派生（§8.7） |
| 公共列 | 每表带 `created_at` / `updated_at` |

**口径裁决**：原型 04·5「历史卷轴」每条显示「正确率 80% · 5 题」且详情页带「重做」按钮 → **列表项 = 一次挑战**，不是一份卷轴；同一卷轴重做会产生多条记录。个人中心「闯关副本 12」与「历史卷轴 12」数字一致，进一步印证。

`attempt_id`(FK)、`question_id`(FK)、`selected`(JSON 选项键数组)、`outcome`（`correct`/`partial`/`wrong`）、`earned_xp`、`max_xp`、`time_spent_ms`、`answered_at`。`UNIQUE(attempt_id, question_id)`。

### 5.7 `reports` — 冒险日志（1:1 于 attempt）

`attempt_id`(UNIQUE, FK)、`user_id`、`status`（`pending`/`ready`/`failed`）、`summary_lines`(JSON，恰好 3 条)、`strong_points`(JSON)、`weak_points`(JSON)、`suggestions`(JSON，每条含 `{title, body, action}`)、`model`、`error_code`、`error_message`、`generated_at`。

> **为什么独立成表而不挂在 `attempts` 上**：报告是**异步生成**且**可独立失败**。挂在一起会让「答题记录（必须成功）」与「AI 报告（可能失败）」的生命周期纠缠——而原型 03·6 明确要求「报告生成失败时答题记录不丢失」。

### 5.8 `wrong_questions` — 错题本

`user_id` + `question_id`（`UNIQUE`）、`wrong_count`、`stage`（0–5）、`next_review_at`、`last_review_at`、`last_wrong_at`、`mastered`（连续两次复习答对置 1，移出队列）。

索引：`idx_user_due (user_id, mastered, next_review_at)`。

### 5.9 `user_knowledge_stats` — 知识树聚合

`user_id` + `kp_name`（VARCHAR(64)，`UNIQUE`）、`total_count`、`correct_count`、`mastery`（`round(correct_count / total_count × 100)`）、`lit`（`mastery ≥ 90` 置 1）、`first_seen_at`、`last_seen_at`。

> **为什么物化而不实时聚合**：知识树与看板的「各知识领域掌握度」都要读它；实时聚合需跨 `answers → questions` 按知识点分组，随数据增长会变成最慢的查询。写入时机只有一处（结算），成本可忽略。

### 5.10 `user_badges` — 勋章解锁记录

`user_id` + `badge_key`（VARCHAR(48)，`UNIQUE`）、`unlocked_at`、`progress_snapshot`(JSON)。

**勋章定义不建表**：18 枚的定义放 `services/badge_service.py` 的常量注册表（`key / name / desc / icon / 条件函数`）。理由：解锁条件需要**代码表达**（如「单局满分且平均每题 < 5 秒」），塞进表里只能存字符串再解释，等于自造一套 DSL。
> 副作用：新增勋章 = 改代码 + 发版。对本项目（单人开发、勋章集稳定）是合适取舍；若日后要做运营侧动态配勋章，再迁表。

### 6.5 结算为什么必须搬到服务端

现状：前端本地判题 + 本地算分。**这个架构与用户系统不相容**——服务端只能信前端上报的结果，档案里的等级、累计 XP、正确率全部可被篡改；反之若服务端不复核，看板画出来的图就没有权威来源。

改造方式（**页面视觉与交互完全不变**）：

1. 答题过程仍在前端即时判题（保证「答对后立刻变绿」不被网络延迟绑架——这条原有决策保留）。
2. 交卷时把**逐题选择**提交后端，由服务端用题目快照重新判定并计分。
3. 结算页展示的数字以**服务端返回为准**；前端的算分模块降级为「即时反馈用」，进入结算页时用服务端结果覆盖。
4. 服务端计算规则与前端的本地规则**逐条对齐**（同一套规则两处实现），并用一组共享用例锁定两边结果一致。

**报告任务保持进程内内存 + TTL，不落库**：任务是**过程态**（用户盯着进度条等十几秒），报告是**结果态**（落 `reports` 表）。进程重启后未完成的任务消失，而 `reports` 行仍为 `pending` → 前端「重新生成报告」即可恢复。这既保留了既有任务服务的简洁，又不会造成数据丢失。

### 7.4 头像与昵称（含隐私合规，**修正 S7 缺口**）

`wx.getUserProfile` 自 2022-10-25 起只返回匿名数据，**不可用**。官方现推「头像昵称填写能力」，本次采用。

**平台侧前置条件（必须由你在管理后台完成）**：配置《小程序用户隐私保护指引》并声明「头像、昵称」等所处理的信息。官方明文：**只有声明过的信息才能调用对应接口或组件；未声明则直接禁用**，报错形如 `api scope is not declared in the privacy agreement`（errno 112）。

**代码侧必须处理的时序**（否则会**静默失效**）：

1. 进入该页时先查询隐私授权同步状态（`needAuthorization`）。
2. 若待同意 → 展示自研或官方弹窗，同意入口使用 `<button open-type="agreePrivacyAuthorization">`，在其回调后再调用隐私能力。
3. 官方另有兜底弹窗，但**不能依赖它**：官方文档明确指出 `<input type="nickname">` 在用户未同意隐私协议时**不会触发隐私授权事件，而是降级为普通文本输入**——用户看到的仍是一个输入框，但微信侧校验已经不在。这正是本项目最需要防的「静默失效」。
4. 基础库 ≥ 2.32.3 才支持隐私查询接口；低于该版本不拦截，因此代码需对能力缺失做兜底而非直接报错。

**页面实现**：头像用 `<button open-type="chooseAvatar">`，昵称用 `<input type="nickname">`，保存走 `PATCH /users/me`。

**入口（2 个）**：07·5 设置页列表**最上方**新增「头像与昵称」（显示当前昵称 + 头像缩略图，符合原型「按使用频率排序」的注释，且不动「账号与安全」的位置）；个人中心身份卡片可点入。

**默认值**：昵称「冒险者 · XXXX」（XXXX 由标识派生 4 位），头像取原型已有的 6 个预置职业头像（学徒 / 学者 / 骑士 / 法师 / 游侠 / 工匠），默认「学者」。因此 `users` 同时保留 `avatar_key`（回退）与 `avatar_url`（自定义，优先）。

**H5 降级**：H5 无 `chooseAvatar` → 用文件选择走**同一个上传接口**；昵称退化为普通输入框。平台差异收敛在工具层，不在页面里散写环境判断。

### 7.5 头像上传的安全要求（**修正 D 类偏差**）

- 大小上限 2 MB；仅接受 jpg / png / webp。
- **校验真实内容**（读取文件头魔数），不只看 Content-Type 与扩展名。
- 文件名由服务端生成（用户 id + 时间戳 + 后缀），**不使用客户端提供的文件名**（防路径穿越与覆盖）。
- 存 `uploads/avatars/`，经静态路径对外提供；静态目录只读、不执行脚本。
- 校验失败 → `4002`。

### 7.6 全局口径延续

| 项 | 处理 |

## 8. 关键业务规则

### 8.1 结算与计分（两处实现，用例锁定）

| 题型 | 满分 |
|---|---|
| 单选 | 40 |
| 多选 | 60 |
| 判断 | 20 |

多选判定顺序：**含错选 → 0 ｜ 全对 → 60 ｜ 非空真子集 → 30 ｜ 空 → 0**。答错不扣分。

- `coins = floor(XP × 0.18)`
- `percentile = clamp(round(accuracy × 0.9), 5, 95)`（演示口径，保留为可替换的 Provider）
- 多选题的部分正确不计入 `correct_count`（与原型「4 / 5」口径一致）

### 8.2 等级曲线（能精确对上原型数字）

```
门槛(1) = 0
门槛(n) = 400 + 800 × (n − 2)   (n ≥ 2)
→ 0, 400, 1200, 2000, 2800, 3600 …
```

验算原型 04·1：`Lv.3` 区间 `[1200, 2000)`，用户 1280 → 本级进度 `1280 / 2000`，「距离 Lv.4 还差 720」= `2000 − 1280` ✓

**原型内部有一处数字冲突**：04·1 上方进度条写 `1280 / 2000`，同屏三宫格又写「累计 XP 1840」，二者不可能同时成立。**裁决**：统一按「累计 XP / 下一级门槛」口径（进度条 `1280 / 2000`、三宫格 `1280`），因为进度条的分母必须是下一级门槛，「还差 720」才成立。

头衔随等级：`见习冒险者`(1–2) → `初级冒险者`(3–4) → `资深冒险者`(5–6) → `史诗冒险者`(7–8) → `传说冒险者`(9+)。（原型只出现「见习冒险者」，其余为自拟）

### 8.3 知识树

`mastery = round(correct_count / total_count × 100)`，`≥ 90` → 点亮。

三态判定必须**先判空**：`total_count = 0` → 「未开始」（不能落进「进行中」）。验算原型：AI 基础 92% → 已点亮 ✓；RAG 80% → 进行中 ✓；评测 0% → 未开始 ✓。

### 8.4 错题复习间隔（原型所说「艾宾浩斯遗忘曲线」）

```
阶段:     0    1    2    3    4    5
间隔(天):  1    2    4    7    15   30
```

- 答错 → `wrong_count + 1`，阶段**回到 0**，下次到期 = 现在 + 1 天。
- 复习答对 → 阶段 +1，下次到期 = 现在 + 间隔[阶段]。
- 连续两次复习答对 → 移出队列（`mastered = 1`）。
- 原型「3 天后」在表里无精确对应（2 天或 4 天），属演示文案；**按上表实现**。

### 8.5 复习提醒（本轮无订阅消息）

原型 04·8 的注释写「从微信服务通知唤回用户的落地页」。**本轮无模板 ID，因此不做真下发**：

- 该页**完整还原原型的视觉与交互**：折纸信使插画、「你有 3 道旧识在等你」、三宫格（预计用时 / 待复习题 / 可得 XP）、「开始重温」+「今天先不复习」。
- 改为**页内提醒**：进入小程序时，若今日有到期错题，在社团大厅与个人中心给出提示入口。
- **订阅消息相关代码一行都不写**：不接订阅授权、不建接口调用凭证缓存、不引入模板配置项。
- 「今天先不复习」→ 写 `remind_snooze_date`，当日不再提示，但**不改变**错题的排期（用户的复习计划不因一次忽略而改变）。
- 将来若要真下发：需在后台建模板并取模板 ID（关键词建议 `thing` 卷轴名 / `number` 待复习题数 / `time` 提醒时间），服务端调用「下发订阅消息」接口，且接口调用凭证有效期 7200 秒需自建缓存并处理限频；小程序端每次下发前需取得该次授权。`subscribe_quota` 列**已在表结构中预留**，届时无需改表。

### 8.7 时区与「今天」（**修正 D6**）

- 数据库统一存 UTC。
- 业务时区固定 `Asia/Shanghai`；「今天」「连续天数」「错题到期」全部按**业务时区**判定，不按 UTC。
- 原因：若按 UTC 判日，北京时间晚上 8 点之后的学习会被算到第二天，直接影响连续天数与到期提醒的正确性。

### 8.8 连续天数

```
今天已有记录 → 不变
last_active_date = 昨天 → streak_days + 1
更早或为空 → streak_days = 1
longest_streak = max(longest_streak, streak_days)
```

| `backend/sql/01_schema.sql` | 建 10 张表（含索引、外键、列注释） | 用 `-D <库名>` 指定目标库；两个库各执行一次；幂等 |

## 12. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 无正式 AppID，登录链路无法自测 | 除登录外全部链路无法在本机验证 | 开发调试通道（§4.7）保证本机可跑通全流程；AppID 到位后真机补验 |
